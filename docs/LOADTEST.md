## Разбор

1. **Падение замечается за 62–92 с — это настройка, не ошибка.** В покое узел анонсирует раз в 30 с (`announceIdleIntervalMs`) и объявляет это в поле `next`; сосед ждёт `next × 3 + 2 с` = 92 с (`PeerRegistry._timeoutFor`). Убитый в случайный момент узел замолкает в среднем на середине периода — отсюда 66–74 с. Порог `peerTimeoutMs` 12 с здесь ни при чём: это лишь нижняя граница. Штатный выход узла быстрый (`bye`), долго только при жёстком обрыве (kill, питание, сеть). Кандидат: сосед, не дождавшийся анонса через `next × 1,5`, один раз проверяет узел через `/peer/ping` и при отказе помечает офлайн сразу — цена один запрос на молчащего.
2. **Потолок в 200–400 узлов на машине — скорее всего TCP, а не UDP.** Вывод заметок («доставка broadcast каждому сокету») не сходится с цифрами: на 200 узлах принято 2400 дейтаграмм/с при CPU 2,5%, на 400 — 3459/с при CPU 93%. Зато на 400: 35 088 соединений, 304 361 отказ `connect ENOBUFS`, 158 247 «нет ответа за 4 с», 5290 `EADDRINUSE`, 545 850 «помечен офлайн». Похоже на лавину: каждый узел тянет `/peer/state` у всех (N² запросов на старте), отказ не гасит повторы (повтор на каждый анонс, темп 3 с), нагрузка растёт ещё сильнее — до отказа очереди процессора. Это **гипотеза**: замеров по состояниям TCP (TIME_WAIT, пул) нет.
3. **Что из этого касается настоящей сети.** На одной машине все узлы делят общий пул портов и ядро — потолок 200–400 здесь не равен потолку для 400 разных компьютеров, где каждый открывает ~N запросов на старте. А вот отсутствие лимита параллельных запросов состояния и отката при отказах — свойство самого кода и важно и там (холодный старт стойки на сотни узлов).
4. **Разброс ±15% — не доказан и не опровергнут.** Сходимость 38,5 против 43,3 с и пик CPU при старте 59 против 65% — в пределах шума одного прогона. Остальные расхождения отчёта — артефакты замера: «UDP в покое 671 против 2716/с» — стенд измерил разные фазы темпа (671 ≈ расчёт для покоя `100 × 99 × 2 / 30`, 2716 — ещё быстрый темп); «возврат 3,2 против 28,6 с» — разница в готовности перезапущенного узла (`victimReadyP50Ms` 2,3 против 28,4 с: старт процесса, не анонсы). Вреда от разброса нет.
5. **Тайм-ауты PowerShell** (7138 на ramp; 72–290 на старте 100 узлов): сотня узлов запускает опрос портов одновременно. На одном узле на машине не встречается; отпечаток из реестра и отложенное полное чтение это и смягчают.
6. **Группы процессоров.** Node видит 64 из 192 логических — процессы стенда живут в одной группе. Для результата 100–200 узлов это не важно, для «сколько выдержит сервер» — важно; проверять не стали.

## Что делать

- Лимит параллельных исходящих запросов состояния (очередь, порядка 8–16) и откат по узлу при отказе (экспоненциально, со сбросом на успех) в `PeerRegistry.refreshPeerState`; затем повторить ramp 200 → 400 → 800 и сравнить с этим прогоном.
- Сосед проверяет молчащий узел `/peer/ping` до истечения 92 с (п. 1).
- При повторе на сервере добавить снимок `netstat -ano | find /c "TIME_WAIT"` и счётчики пула во время ступени 400 — чтобы подтвердить или снять п. 2.
