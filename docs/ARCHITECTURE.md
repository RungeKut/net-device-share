# Устройство приложения

## Из чего оно состоит

```
                 ┌──────────────────────── main.js ───────────────────────┐
                 │  разбор аргументов, --doctor, корректное завершение     │
                 └────────────────────────────┬───────────────────────────┘
                                              │
                 ┌──────────────────────── core/app.js ───────────────────┐
                 │  сборка, единый снимок состояния, применение настроек   │
                 └──┬──────────┬──────────┬──────────┬──────────┬─────────┘
                    │          │          │          │          │
        ┌───────────▼──┐ ┌─────▼─────┐ ┌──▼───────┐ ┌▼────────┐ ┌▼────────────┐
        │ discovery.js │ │ peers.js  │ │ share    │ │ attach  │ │ httpServer  │
        │ кто есть     │ │ реестр    │ │ Manager  │ │ Manager │ │ UI + RPC    │
        │ в сети (UDP) │ │ соседей   │ │ свои     │ │ чужие   │ │             │
        └──────────────┘ └───────────┘ └────┬─────┘ └────┬────┘ └─────────────┘
                                            └─────┬──────┘
                                        ┌─────────▼─────────┐
                                        │  usb/backend.js   │
                                        │  windows │ linux  │
                                        │      │ mock       │
                                        └─────────┬─────────┘
                                          usbipd / usbip / sysfs
```

Каждый модуль отвечает ровно за одно, а связь между ними — события и вызовы
в одну сторону: `app` знает про всех, никто не знает про `app`.

## Решения, которые определили остальное

### Владелец — единственный источник истины о занятости

Устройство принадлежит одному узлу. Он и решает, кто его занимает. Остальные
хранят копию его состояния.

Альтернатива — общий распределённый реестр, который синхронизируют все узлы, —
потребовала бы выбора лидера, кворума и разрешения конфликтов при разделении
сети. Ради задачи, где спорное состояние по определению принадлежит одной
машине, это чистые потери. Здесь split-brain невозможен как класс: конфликт
разрешается тем, что второй запрос получает `409 busy` от той же машины,
которая выдала первое право.

### Занятость — аренда, а не флаг

Право выдаётся на 30 секунд и продлевается heartbeat-ами, пока клиент работает.

Постоянный флаг ломается на первой же аварии: клиент выключили из розетки —
устройство заблокировано навсегда, пока владелец не вмешается руками. Аренда
делает восстановление автоматическим и не требует от узлов доверия к чужой
дисциплине освобождения.

### Право и подключение — разные шаги, и порядок важен

Занятие: сначала спросить право у владельца, потом трогать локальный VHCI.
Отказали — локальная система не затронута вовсе.

Освобождение: сначала отцепить, потом вернуть право. Иначе владелец успел бы
отдать устройство следующему, пока у нас оно ещё подключено.

Если подключение сорвалось уже после выдачи права, клиент возвращает право сам
(`attachManager.attach`, ветка `catch`): устройство не должно оставаться занятым
из-за неудачи на чужой стороне.

### Анонсы несут хеш, а не данные

UDP-датаграм обязан помещаться в MTU и не расти от числа устройств. Поэтому
анонс — это идентичность плюс `stateHash`. Сосед видит, что хеш изменился, и
забирает состояние по HTTP. Не изменился — не делает ничего.

Побочная выгода: HTTP даёт внятные ошибки и подтверждение доставки там, где они
действительно нужны, а UDP остаётся только для того, для чего он хорош, —
дешёвого периодического «я здесь».

### Multicast и broadcast одновременно

Полагаться на один multicast нельзя: в корпоративных сетях и на Wi-Fi-точках он
часто отключён, и узлы бы просто не нашли друг друга. Анонс идемпотентен, обе
копии безвредны.

### Одна кодовая база для сервера и клиента

Разделять на два приложения незачем: у обеих ролей общие каталог устройств,
реестр соседей, транспорт и интерфейс. Роли различаются лишь тем, какие методы
бэкенда вызываются. Именно поэтому занять собственное устройство — не особый
случай, а тот же путь с адресом своего же узла.

### Вся платформенная специфика — за одним интерфейсом

`UsbBackend` — пять методов: `probe`, `listLocal`, `bind`/`unbind`,
`attach`/`detach`, `listAttached`. Выше этой границы код не знает ни про
`usbipd.exe`, ни про sysfs.

Проверка среды (`probe`) раздельно сообщает про роль сервера и роль клиента,
потому что на Windows они ставятся разными пакетами и наличие одной ничего не
говорит о другой.

Бэкенд `mock` — не декорация: он позволяет прогнать весь сетевой сценарий между
настоящими машинами без драйверов и без прав администратора.

### Недостающее ставится оттуда же, где о нём сообщают

Сообщение «не хватает компонента» без способа его поставить отправляет
пользователя читать документацию ради того, что делается одной кнопкой.
Поэтому кнопка «Установить» живёт прямо в баннере с проблемой
(`src/core/installer.js`).

Установщики вложены в проект, а не скачиваются по требованию: приложение
разворачивают в том числе там, где интернета нет вовсе. Плата за это —
около 30 МБ в репозитории; взамен установка работает всегда и одинаково.

Перед запуском файлы проверяются по SHA-256 из манифеста и по подписи
Authenticode. Это не формальность: мы запускаем установщик драйвера ядра с
правами администратора, а папку рядом с приложением мог подменить кто угодно
с доступом к диску. Не сошлось — установка отменяется целиком, без попыток
«поставить хотя бы что-то».

### Установщики запускаются напрямую, а не через сброшенный сценарий

Сначала было иначе: приложение писало в `%TEMP%` файл `.ps1` и запускало его
от администратора с `-ExecutionPolicy Bypass` — ради одного запроса UAC на все
компоненты сразу.

Решение пришлось развернуть. «Сбросил сценарий во временную папку → обошёл
политику исполнения → поднял права» — дословное описание поведения загрузчика
вредоносного кода, и антивирусы помечают такую связку эвристикой. Претензия
справедлива: со стороны отличить нельзя. Пугать пользователя предупреждением
о трояне в собственном приложении недопустимо — доверие дороже одного лишнего
щелчка.

Теперь каждый установщик запускается напрямую, а PowerShell остаётся тонкой
обёрткой над ShellExecute с глаголом `RunAs`: вызвать его из Node иначе
нельзя. Команда короткая и постоянной формы, а `-Command` под политику
исполнения не подпадает — она действует на файлы сценариев.

Плата — отдельный запрос UAC на каждый компонент. Но это не только плата:
в окне теперь виден издатель настоящего установщика («Frans van Dorsselaer»,
«Cloudyne Systems»), а не безликое «Windows PowerShell». Прежний вариант
обосновывался тем, что пользователь должен понимать, на что соглашается, —
новый выполняет это требование лучше.

Тот же урок применён в `openBrowser` (`src/main.js`): там был `cmd /c start`
со скрытым окном и отвязкой от родителя — по тем же причинам заменён на
`explorer.exe`. Общее правило для этого проекта: **не делать того, что
неотличимо от вредоносного поведения**, даже когда это удобнее.

## Что происходит при занятии устройства

```
 UI(Б) ──POST /api/v1/attach──▶ app(Б).attachDevice
                                     │ находит владельца в реестре соседей
                                     ▼
                              attachManager.attach
                                     │
          ┌──── POST /api/v1/peer/claim ────────────────▶ shareManager(А).claim
          │                                                 проверяет публикацию
          │                                                 проверяет занятость
          │                                                 backend(А).bind(busid)
          │                                                 ставит аренду до T+30с
          │◀─────── 200 {usbipPort, leaseMs} ───────────────┘
          ▼                                              А анонсирует новый хеш
   backend(Б).attach({host, busid})
          │  usbip attach -r А -b 1-4
          ▼
   устройство в «Диспетчере устройств» Б
          │
          └── каждые 10 с: POST /api/v1/peer/heartbeat ──▶ продление аренды
```

Если `backend(Б).attach` упадёт, право будет возвращено немедленно, а запись о
подключении удалена — состояние не «залипнет» ни на одной из сторон.

## Состояние и интерфейс

Интерфейс не собирает состояние из кусочков: сервер отдаёт **весь снимок**
целиком (`app.snapshot()`), по SSE, при каждом изменении. Частичные обновления
пришлось бы сшивать на клиенте, и экран рано или поздно разошёлся бы с
реальностью — особенно там, где события приходят и от локальных действий, и от
соседей по сети.

В снимке каталог устройств уже склеен: свои опубликованные и чужие лежат в одном
массиве с одинаковыми полями и признаками `ownerSelf`, `busy`, `busyByMe`.
Интерфейсу остаётся только нарисовать.

Разграничение доступа — на уровне маршрутов, а не сокета. HTTP-сервер слушает все
интерфейсы, потому что к нему обращаются соседи, но всё, что меняет настройки
этого узла, принимается только с `127.0.0.1`.

## Следующий шаг: COM и LPT

Проект назван обобщённо не заранее, а по плану: следующими в общий доступ
пойдут последовательные и параллельные порты. Почти всё, что для этого нужно,
уже есть и от типа устройства не зависит — обнаружение узлов, каталог, аренда
и занятость, имена узлов, интерфейс, установка компонентов.

Менять придётся только слой устройств. Разумный порядок:

1. Переименовать `src/usb/` в `src/devices/` и ввести понятие **типа
   устройства** (`usb` | `com` | `lpt`) в модели и в каталоге: сейчас тип
   подразумевается, а не хранится.
2. Обобщить `UsbBackend` до `DeviceBackend`. Пять его методов ложатся на COM
   почти без натяжки: `listLocal` — перечисление портов, `bind`/`unbind` —
   захват порта, `attach`/`detach` — создание виртуального порта у клиента.
3. Добавить реализацию для COM. Транспорт здесь не USB/IP, а свой: RFC 2217
   (Telnet COM Port Control) — готовый стандарт, под который есть и серверы,
   и клиентские драйверы виртуальных портов. Значит, у бэкенда появится второй
   транспорт, и порт данных перестанет быть одним на всё приложение.
4. Заложить в протокол поле типа заранее: узлы разных версий должны
   игнорировать устройства незнакомых типов, а не падать на них.

Главное, что не нужно трогать: модель занятости. Право на COM-порт выдаётся
ровно так же, как на USB-устройство, — владельцем, арендой, с теми же
heartbeat-ами.

## Что стоит сделать дальше

* **Служба Windows и юнит systemd** — сейчас приложение живёт в окне консоли.
* **Автоподключение** избранных устройств при их появлении в сети.
* **Очередь ожидания** на занятое устройство вместо отказа `409 busy`.
* **Шифрование трафика USB/IP** — сам протокол его не даёт; пока решается VPN.
* **Сборка в один исполняемый файл** через `node --experimental-sea-config`,
  чтобы не требовать установленного Node.js.
* **Автотесты** — сценарии в `docs/` пока проверяются вручную запуском двух
  экземпляров с `--backend mock`.
