# Протокол NDS/1

Обмен между узлами разнесён по двум каналам, и это главное решение протокола.

| Канал | Транспорт | Что несёт | Почему так |
|---|---|---|---|
| Присутствие | UDP multicast + broadcast, порт 47811 | идентичность узла и **хеш** его состояния | пакет обязан помещаться в один датаграм и не расти от числа устройств |
| Состояние и действия | HTTP поверх TCP, порт 47812 | список устройств, занятие, освобождение, heartbeat | нужен надёжный запрос-ответ с внятными кодами ошибок |

Список устройств по UDP **не передаётся никогда**. Анонс несёт только
`stateHash`; сосед замечает, что хеш изменился, и забирает состояние по HTTP.
На сети из двадцати узлов с постоянными анонсами это разница между
несколькими сотнями байт в секунду и потоком мусора, упирающимся в MTU.

---

## 1. Канал присутствия (UDP)

Каждый датаграм — конверт:

```json
{ "sig": "<HMAC-SHA256 от body в hex, либо пустая строка>", "body": "<JSON-строка>" }
```

Подписывается именно строка `body`, а не разобранный объект: подпись обязана
считаться от того, что реально пришло по сети, иначе порядок ключей при
пересериализации ломал бы проверку.

### Анонс — адаптивный темп

```json
{
  "proto": "nds/1",
  "type": "announce",
  "nodeId": "b0f7…",          // UUID, переживает перезапуск
  "realm": "open",            // круг доверия, производная от ключа
  "name": "СТЕНД-А",
  "seq": 128,
  "ts": 1757942400000,
  "apiPort": 47812,
  "usbipPort": 3240,
  "network": "192.168.1.0/24",
  "platform": "win32",
  "version": "1.0.0",
  "startedAt": 1757940000000,
  "stateHash": "9c1a5f2e7b04d3aa",
  "deviceCount": 3,
  "busyCount": 1
}
```

### Прочие типы

* `query` — «представьтесь немедленно». Отправляется при старте, чтобы не ждать
  первого цикла анонсов.
* `bye` — узел корректно уходит. Соседи убирают его сразу, не выжидая таймаут.

### Приём пакета: три фильтра подряд

1. **Адрес отправителя внутри рабочего CIDR** — иначе пакет не наш. Отсекает
   виртуальные адаптеры Hyper-V и WSL, VPN-туннели и чужие сегменты.
2. **Подпись верна** — при заданном ключе. Пустой ключ проверку отключает.
3. **`realm` совпадает** — иначе это другой круг доверия.

Третий фильтр существует потому, что одной подписи мало: узел **без** ключа
принимает любые пакеты и иначе показывал бы в списке узлы с ключом, до которых
не может достучаться. `realm` — это `sha256("nds-realm/1:" + ключ)`, обрезанный
до 16 символов, либо строка `open` при пустом ключе. Ключ по нему не
восстанавливается.

### Multicast и broadcast одновременно

Анонс уходит на `239.255.77.66` **и** на широковещательный адрес подсети.
В части корпоративных сетей и на многих Wi-Fi-точках multicast режется, и без
дублирования broadcast-ом узлы просто не нашли бы друг друга. Анонс идемпотентен,
поэтому получить обе копии безвредно.

### Несколько кругов доверия

Подпись в пакете одна, а кругов у узла может быть несколько, поэтому
анонс уходит **по разу на каждый круг**: узел с ключом «Цех» обязан принять
наш пакет, и узел с ключом «Лаборатория» тоже, а один пакет удовлетворить
обоим не может. Трафик умножается на число кругов — замедление в покое с
несколькими сетями важнее, чем с одной.

На приёме ключ выбирается по полю `realm` из самого пакета, и лишь потом
проверяется подпись. Тело поэтому разбирается до проверки: перебирать все
ключи на каждом чужом пакете дороже. До проверки из тела берётся ровно одно
поле — `realm`, и только чтобы выбрать ключ.

Открытый круг (`realm` = `open`) ключа не имеет. Пакет в нём принимается,
только если подписи нет **вовсе**: иначе пакет из чужой ключевой сети,
объявивший себя открытым, прошёл бы как свой — проверка пустым ключом
принимает что угодно.

В HTTP метка круга не передаётся: подпись проверяется перебором наших
ключей, ключевые первыми, открытый — последним и только для запросов без
подписи. Порядок здесь обязателен по той же причине.

### Темп анонсов и поле `next`

Анонс получает каждый компьютер подсети, поэтому ровный темп в три секунды —
это постоянный широковещательный фон, не зависящий от того, происходит
что-нибудь или нет. Темп адаптивный:

* состояние изменилось → интервал возвращается к `announceIntervalMs` (3 с);
* очередной анонс без изменений → интервал удваивается до
  `announceIdleIntervalMs` (30 с);
* изменение, которое нечего объявлять (хеш тот же), анонса не порождает вовсе.

Замедлившийся узел обязан сказать соседям, когда его ждать, иначе они сочтут
его пропавшим по своему таймауту. Для этого в анонсе едет **`next`** —
интервал до следующего анонса в миллисекундах. Сосед считает таймаут как
`next × 3 + 2 с`, но не меньше `peerTimeoutMs`.

Поле **`dir`** — отпечаток каталога узлов из других сетей. Непустой только у
узла, который сам ходит к настроенным адресам или к которому пришли извне.
Соседи по подсети видят изменившийся отпечаток и забирают каталог по HTTP.

### Тайминги

| Событие | Порог |
|---|---|
| интервал анонсов | 3 с |
| узел помечается недоступным | 12 с молчания (4 пропущенных анонса) |
| узел удаляется из списка | 120 с |

## 2. Канал состояния и действий (HTTP)

Порт один с интерфейсом, но доступ разграничен:

* `/api/v1/peer/*` — вызовы других узлов: проверяются CIDR и подпись;
* всё остальное — интерфейс и управление: **только с локального адреса**.

Подпись передаётся в заголовке `X-Nds-Auth`, идентификатор вызывающего —
в `X-Nds-Node`. Подписывается точное тело запроса (для GET — пустая строка).

### `GET /api/v1/peer/state`

Полное состояние узла: `nodeId`, `name`, `version`, `startedAt`, `platform`,
`apiPort`, `usbipPort`, `stateHash` и `devices` — массив **только
опубликованных** устройств:

```json
{
  "busid": "1-4",
  "vendorId": "0403", "productId": "6001",
  "description": "FTDI USB Serial Converter",
  "serial": "FT1ABCD2",
  "shared": true,
  "bindState": "bound",
  "claim": { "holderId": "…", "holderName": "НОУТБУК-Б",
             "since": 1757942100000, "expiresAt": 1757942130000, "mode": "remote" },
  "connectedSince": 1757900000000,
  "sharedSince": 1757941000000,
  "note": "ключ ЭЦП для бухгалтерии",
  "lastError": null
}
```

### `POST /api/v1/peer/claim`

Запрос `{ "busid": "1-4", "holderId": "…", "holderName": "НОУТБУК-Б" }`.

| Ответ | Значение |
|---|---|
| `200` | право выдано: `{ ok, busid, usbipPort, leaseMs, claim, device }` |
| `409 busy` | занято другим; в теле `claim` с именем занявшего |
| `404 device_not_found` | устройство отключили |
| `400 not_shared` | владелец снял публикацию |
| `400 bind_failed` | драйвер не отдал устройство (обычно — нет прав администратора) |

Повторный `claim` от того же держателя не ошибка, а продление аренды: так
перезапустившийся клиент возвращает себе устройство без конфликта.

### `POST /api/v1/peer/heartbeat`

`{ "busid": "1-4", "holderId": "…" }` → `200 { ok, expiresAt }`.
Шлётся раз в 10 с. `409 no_claim` или `403 forbidden` означают, что право
отозвано — клиент обязан немедленно отцепить устройство.

### `POST /api/v1/peer/release`

`{ "busid": "1-4", "holderId": "…" }` → `200`. Освободить может только держатель;
принудительно — только владелец устройства, и только через свой локальный
интерфейс.

### `GET` / `POST /api/v1/peer/directory`

Каталог узлов — знакомство между сетями. Обнаружение по UDP не выходит за
пределы подсети: broadcast не маршрутизируется, multicast в корпоративных
сетях обычно тоже. Поэтому узлы обмениваются списками поверх HTTP.

`GET` отдаёт наш каталог. `POST` принимает чужой и отвечает своим — один
запрос, обмен в обе стороны. Благодаря этому настроить достаточно **одну**
сторону: вторая узнаёт о первой из того же запроса.

```json
{
  "nodeId": "...", "name": "СТЕНД-1", "network": "10.1.0.0/24", "ts": 1699999999,
  "peers": [
    { "nodeId": "...", "name": "СТЕНД-2", "address": "10.2.0.7",
      "apiPort": 47812, "usbipPort": 3240, "network": "10.2.0.0/24",
      "platform": "win32", "version": "2.0.0", "startedAt": 1699990000,
      "stateHash": "a1b2c3d4e5f60718", "deviceCount": 4, "busyCount": 1 }
  ]
}
```

**В каталоге нет ни списков устройств, ни занятости.** Только «кто есть и по
какому адресу». Всё остальное каждый узел спрашивает у владельца напрямую,
поэтому нагрузка на узел-посредник не зависит от того, сколько в сети
устройств и как интенсивно ими пользуются.

Адрес в записи — собственный адрес узла и таким же уходит дальше по цепочке
пересказов. Кто бы о узле ни рассказал, обращаться к нему будут напрямую.
(Из этого следует ограничение: между сетями нужен маршрут, а узлы за NAT так
работать не будут.)

#### Откуда узел известен и кому о нём рассказывать

Каждая запись реестра помечена источником:

| origin | откуда | рассказываем дальше |
|---|---|---|
| `local` | услышан по multicast/broadcast | да |
| `seed` | от узла из другой сети | да |
| `relay` | от моста в своей подсети | **нет** |

Источник определяется адресом собеседника: вызов из нашей подсети — это
пересказ (`relay`), вызов извне — знакомство с другой сетью (`seed`).
Запрет пересказывать пересказ ограничивает распространение ровно одним
шагом: этого хватает, чтобы связать сегменты, и мало, чтобы устроить лавину.

Услышанный вживую сосед всегда важнее пересказанного: анонс переводит узел
в `local` и его данные каталогом уже не подменяются.

#### Круг доверия проверяется до отправки

Перед обменом инициатор запрашивает `GET /api/v1/peer/ping` и сверяет поле
`realm`. Не совпало — каталог не отправляется вовсе, а адрес помечается в
настройках как «другой круг доверия».

Проверять это только на приёмной стороне мало: узел **без** ключа принимает
любую подпись, поэтому отправка каталога сразу означала бы отдать ему карту
всей своей сети — включая узлы, которых он по обычному обнаружению не видит.
Приёмная сторона тоже сверяет `realm` и отвечает `403 other_realm`, но
основную защиту даёт проверка до отправки.

#### Доступ из другой сети

Вызов `/api/v1/peer/*` с адреса вне рабочей подсети принимается **только
при заданном общем ключе**. Внутри подсети границу доверия держит адрес:
чужому надо сперва в неё попасть. За её пределами такой границы нет, и
единственной остаётся подпись — а без ключа подпись не проверяется вовсе.
Без ключа такой вызов отвергается с `403 out_of_network`.

### `GET /api/v1/peer/ping`

Отдаёт идентичность и `stateHash`. Нужен узлам из других сетей: анонсов от
владельца они не слышат, а тянуть полный список устройств ради ответа «всё
по-прежнему» — лишний трафик через маршрутизатор. Полное состояние
запрашивается, только когда хеш разошёлся.

## 3. Модель занятости

**Решение принимает владелец устройства и никто больше.** Это устраняет саму
возможность расхождения реплик: состояние устройства существует ровно в одном
месте, остальные узлы хранят его копию и перечитывают при изменении хеша.
Ни выборов лидера, ни кворума, ни split-brain.

Право — это **аренда** с конечным сроком (по умолчанию 30 с), а не постоянный
флаг. Клиент продлевает её heartbeat-ами, пока работает с устройством. Если
клиент исчез — выключили питание, оборвалась сеть, упал процесс — аренда
истечёт и владелец освободит устройство сам. Флаг без срока в этой ситуации
заблокировал бы устройство навсегда.

### Полный цикл

```
клиент Б                         владелец А
   │  POST peer/claim  ──────────▶ проверяет: опубликовано? свободно?
   │                               usbipd bind 1-4
   │  ◀────────── 200 {usbipPort}  ставит аренду до T+30 с
   │                               анонсирует новый stateHash
   │  usbip attach -r A -b 1-4
   │  ═══════ данные USB/IP (TCP 3240) ══════▶
   │  устройство в «Диспетчере устройств»
   │
   │  POST peer/heartbeat ───────▶ аренда до T+40 с   (каждые 10 с)
   │
   │  usbip detach -p N
   │  POST peer/release ─────────▶ usbipd unbind 1-4
   │                               аренда снята, новый stateHash
```

### Отдельные случаи

* **Занятие своего устройства** — штатный сценарий, `mode: "local"`. Соседи
  видят его занятым вами. Право запрашивается напрямую, без обращения к сети;
  подключение идёт через собственный LAN-адрес.
* **Устройство выдернули из разъёма** — владелец снимает аренду и уведомляет об
  этом: держать право на отсутствующее оборудование бессмысленно.
* **Владелец отобрал устройство** — аренда снимается принудительно. Клиент
  узнаёт об этом по ответу на очередной heartbeat и отцепляет устройство, чтобы
  в его системе не осталось записи, ведущей в никуда.
* **Сетевой сбой у клиента** — три неудачных heartbeat-а подряд, только потом
  отключение. Рвать рабочее подключение из-за одного потерянного пакета нельзя.
* **Ошибка при подключении после выдачи права** — клиент возвращает право сам,
  иначе устройство осталось бы занятым из-за неудачи на чужой стороне.

## 4. Порты

| Порт | Протокол | Назначение | Кто должен открыть |
|---|---|---|---|
| 47811 | UDP | обнаружение узлов | все узлы |
| 47812 | TCP | интерфейс и межузловой RPC | все узлы |
| 3240 | TCP | данные USB/IP | тот, кто раздаёт устройства |

Порты 47811 и 47812 меняются параметрами запуска; 3240 задан протоколом USB/IP.

## 5. Версия 2: типы, группы, запросы, уровни доступа

### Идентификаторы целей

Устройство больше не адресуется одним `busid`: типов стало четыре. Составной
идентификатор — `<тип>:<локальный ключ>`:

```
usb:1-4        USB-устройство на шине 1-4
com:COM19      последовательный порт
lpt:LPT1       параллельный порт
net:Ethernet   сетевой интерфейс (именно интерфейс, а не карта)
```

Во всех вызовах занятости фигурирует не устройство, а **цель** (`target`) —
либо идентификатор устройства, либо `group:<id>`. Это позволило не заводить
отдельный набор методов для групп: занятие, продление, освобождение и запросы
одинаковы для одиночного устройства и для составного.

Тип в самом ключе избавляет от параллельных пространств имён и делает записи
самообъясняющими в журналах.

### Группы в состоянии узла

`GET /api/v1/peer/state` дополнен двумя полями:

```json
{
  "devices": [ … ],
  "groups": [
    { "id": "g_1a2b3c4d", "name": "Стенд STM32",
      "description": "JTAG и консоль одной платы — занимать только вместе",
      "members": ["usb:1-4", "com:COM19"],
      "available": true, "partial": false,
      "claim": { "holderId": "…", "holderName": "НОУТБУК-Б", "since": 1757942100000 },
      "reservedFor": null }
  ],
  "requests": [ … ]
}
```

`requests` отдаётся **отфильтрованным**: узел получает только те запросы, где
он проситель или держатель. Чужие переговоры его не касаются.

Группа занимается **атомарно**: владелец проверяет все её устройства до того,
как тронуть хоть одно, и при неудаче на любом откатывает уже сделанное. Иначе
между захватом первого устройства и второго вклинился бы третий узел, и оба
устройства оказались бы бесполезны.

### Запросы на занятую цель

```
проситель В            владелец А                держатель Б
   │ POST peer/request ──▶ создаёт запрос
   │                       │ POST peer/notify-request ──▶ диалог у Б
   │                       │        (heartbeat донесёт и без этого)
   │                       │
   │                       ◀── POST peer/request-answer {accept} ──│
   │                       освобождает цель, ставит бронь за В (45 с)
   │ ◀── состояние: accepted ──┘
   │ POST peer/claim ──▶ занимает (бронь пускает только его)
```

| Запрос | Назначение |
|---|---|
| `POST /api/v1/peer/request` | попросить занятую цель; в теле `target`, `requesterName`, `message` |
| `POST /api/v1/peer/request-answer` | ответ держателя: `requestId`, `accept` |
| `POST /api/v1/peer/notify-request` | владелец → держателю: мгновенное уведомление |
| `POST /api/v1/peer/revoked` | владелец → держателю: право отозвано, отцепись |

Два последних нужны только ради скорости: ответ на heartbeat донёс бы и запрос,
и отзыв сам, но с задержкой до десяти секунд. Диалог должен всплывать сразу, а
отобранное устройство — исчезать из системы держателя сразу, а не висеть
мёртвым узлом. Если мгновенное уведомление не прошло, heartbeat остаётся
надёжным запасным путём: доставка гарантирована, просто позже.

**Бронь после согласия.** Держатель согласился — цель освобождается и на 45
секунд закрепляется за просителем. Без этого согласие часто уходило бы впустую:
между освобождением и попыткой просителя занять цель вклинился бы кто угодно.

**Право владельца.** `force` в `peer/claim` **игнорируется**: чужой узел не
может забрать устройство без спроса. Преимущественное право действует только
на своём узле — через локальный `POST /api/v1/attach` с `force: true`.
Оборудование стоит у владельца на столе, и это единственное место, где такое
решение уместно.

### Уровни доступа к интерфейсу

Порт по-прежнему один, но уровней теперь три:

| Уровень | Кто | Что можно |
|---|---|---|
| `peer` | другие узлы, `/api/v1/peer/*` | подпись + принадлежность к рабочей сети |
| `full` | локальный адрес либо действительная сессия | всё |
| `readonly` | любой другой адрес | только чтение состояния |

Вход: `POST /api/v1/login` с паролем → cookie `nds_session` вида
`<срок>.<HMAC>`, `HttpOnly`, `SameSite=Strict`, 12 часов. Список выданных
сессий нигде не хранится: подпись проверяется вычислением, а срок ограничивает
ущерб от утёкшей cookie. Пароль хранится только как scrypt-хеш со случайной
солью; сравнение идёт за постоянное время.

Все изменяющие вызовы требуют `full`. В режиме `readonly` интерфейс не рисует
кнопок, но полагаться на это нельзя — права проверяет сервер.

### Публикация группы

У группы есть собственный флаг `shared`, и он определяет, кто распоряжается
её устройствами:

| Состояние группы | Устройства группы |
|---|---|
| опубликована | отдаются наружу группой; поодиночке не публикуются и не занимаются |
| не опубликована | ведут себя как обычные: публикуются и занимаются по отдельности |

`POST /api/v1/group/share` с `groupId` и `shared` переключает состояние.
Снять публикацию у занятой группы нельзя — сначала освободить.

Соседям уходят только опубликованные группы: неопубликованная существует
лишь как заготовка у владельца. В `GET /api/v1/peer/state` список `devices`
поэтому включает и членов опубликованных групп, даже если сами по себе они
не опубликованы, — иначе группа приходила бы соседу неполной.

### Учёт трафика

Данные USB/IP идут между драйвером клиента и службой usbipd мимо приложения,
поэтому «изнутри» их не посчитать. Единственный способ узнать точный объём по
каждому устройству — встать в разрыв соединения:

```
клиент                    владелец
  │ usbip -t 47813 attach ──▶ счётчик (47813)
  │                             │ считает байты в обе стороны
  │                             ▼
  │                          usbipd (3240)
```

Клиенту сообщается не 3240, а порт счётчика: он приходит в ответе на
`peer/claim` полем `usbipPort`, а `usbip` умеет подключаться к произвольному
порту (`--tcp-port`). Кому принадлежит соединение, выясняется из первого
пакета: протокол USB/IP начинается с `OP_REQ_IMPORT`, где открытым текстом
лежит busid.

**Точные байты в `stateHash` не входят.** Они меняются каждую секунду, и
соседи перечитывали бы состояние без остановки. В хеш идёт только признак
«есть активность»: переход «молчит ↔ работает» доходит быстро, а сами цифры
держатель получает в ответе на `peer/heartbeat` — он и так приходит каждые
десять секунд.

Показывается объём **за последнюю минуту** (кольцо из шестидесяти секундных
отсчётов), а не мгновенная скорость: минута сглаживает рывки USB-обмена, и по
ней видно, работает устройство или просто числится занятым.

Учёт отключается настройкой `meterTraffic`. Тогда клиентам сообщается порт
usbipd напрямую, посредника в тракте данных нет, а цифры не показываются.
Если порт счётчика занят или сокет отказал, приложение само откатывается на
прямое соединение — измерения полезны, но не ценой работы устройств.
