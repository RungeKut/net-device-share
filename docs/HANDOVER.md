# Передача проекта

Документ для того, кто продолжает работу — на другом компьютере или после
перерыва. Здесь состояние дел, порядок развёртывания, принятые решения и,
главное, **список уже собранных граблей**: на них потрачено время, и
наступать повторно незачем.

Версия 2.0.0.

> Проект живёт в двух местах: внутренний GitLab (основная работа) и
> публичная копия на GitHub. Адрес внутреннего репозитория сознательно
> здесь не указан — документ попадает в публичную копию; спросите его у
> владельца проекта.

## 1. Что это

Приложение-узел для совместного доступа к устройствам по локальной сети.
Каждый участник запускает **одну и ту же программу**: она одновременно
раздаёт свои устройства и занимает чужие. Централизованного сервера нет.

Node.js, **ноль зависимостей**, без шага сборки. Около 13 тысяч строк, из
них примерно четверть — интерфейс; ещё 1500 строк PowerShell и C# в
`scripts/` (всё, что Node не умеет: TAP, мост, SetupAPI). `npm install`
не нужен.

## 3. Развёртывание на новой машине

```
git clone <адрес репозитория>
cd net-device-share
node src/main.js --doctor
```

Нужен **Node.js 20.6+**. Зависимостей нет, ставить нечего.

### Переносимый комплект для Windows

```
npm run build
```

Собирает `dist/net-device-share-<версия>-win-x64/` и `.zip` к нему (~34 МБ).
Внутрь кладётся `node.exe` зафиксированной версии — на целевой машине Node
ставить не нужно. Версия и её SHA-256 прописаны в `scripts/build-release.mjs`;
скачанное кэшируется в `dist/.cache/`, поэтому повторная сборка идёт без сети.

Оба пусковых файла проверяют `node.exe` рядом с собой и предпочитают его
системному. Комплект обязан вести себя одинаково на любой машине, поэтому
приоритет именно такой, а не наоборот.

Установщиков USB/IP в архиве нет (GPL-3.0, см. ниже) — едут только манифест и
скрипт загрузки. Без драйверов комплект работает как каталог устройств.

### Установщики драйверов загружаются отдельно

Каталог `installers/windows` в репозитории пуст: usbipd-win и usbip-win2
распространяются под GPL-3.0, и выкладывать их сборки у себя значит принимать
обязательства по выдаче исходных текстов. Манифест с адресами и контрольными
суммами лежит в репозитории, файлы берутся по нему:

```
node scripts/fetch-installers.mjs
```

Загруженное проверяется по SHA-256 из манифеста — ровно так же, как
проверялось бы вложенное. Без этого шага всё работает, кроме кнопки
«Установить»: приложение просто скажет, что файлов нет.

### Если репозиторий за корпоративным прокси

Когда в окружении задан `HTTPS_PROXY`, а сервер за ним недоступен (типично
для внутренних адресов), git падает с `503 from proxy after CONNECT`.
Лечится отключением прокси для конкретного адреса. Настройка **локальная и
в коммит не попадает**, поэтому на каждой новой машине её надо повторить:

```
git config --local "http.https://<хост>/.proxy" ""
```

### Windows: драйверы

Запустить `start.bat`. Если чего-то не хватает — в шапке появится кнопка
«Установить»: файлы лежат в `installers/`, интернет не нужен. Подробности —
[WINDOWS-SETUP.md](WINDOWS-SETUP.md).

Права администратора обязательны: без них `usbipd bind` не работает и
публикация устройств падает с ошибкой.

### Где лежат настройки

`%APPDATA%\net-device-share\config.json` (Windows),
`~/.config/net-device-share/config.json` (Linux).
Переменная `NDS_HOME` задаёт свой каталог — так на одной машине поднимается
несколько независимых узлов (нужно для тестов).

## 5. Решения, которые не стоит пересматривать вслепую

За каждым стоит потраченное время. Если решите менять — сначала прочтите
обоснование в [ARCHITECTURE.md](ARCHITECTURE.md).

**Владелец — единственный источник истины о занятости.** Не заводить общий
распределённый реестр: спорное состояние по определению принадлежит одной
машине, консенсус здесь — чистые потери.

**Занятость — аренда с heartbeat, а не флаг.** Флаг ломается на первой
аварии: клиента выключили — устройство заблокировано навсегда.

**Группа занимается атомарно.** Проверка идёт по всем устройствам до того,
как тронуто хоть одно. Иначе между двумя захватами вклинивается третий узел.

**Анонсы несут хеш, а не данные.** UDP-пакет обязан помещаться в MTU.
Точные байты трафика в хеш **не входят** — иначе соседи перечитывали бы
состояние каждую секунду.

**Установщики запускаются напрямую, без временных сценариев и без
`-ExecutionPolicy Bypass`.** Прежний вариант антивирусы справедливо считали
загрузчиком вредоносного кода. Общее правило проекта: **не делать того, что
неотличимо от вредоносного поведения**, даже когда это удобнее.

**Локально — всё без пароля, извне — по паролю.** У того, кто сидит за
машиной, и так есть все возможности: он может выдернуть кабель. Но
«локально» — это любой запрос с этой машины, в том числе от посторонней
страницы в браузере; поэтому изменяющие запросы интерфейса несут заголовок
`X-NDS-UI`, которого такая страница послать не может.

**TAP-адаптеры создаются по одному (SetupAPI), а не devcon.** `devcon
install` переустанавливает драйвер на всех TAP сразу и обрывает работающие
пробросы, коммутаторы и туннели OpenVPN. devcon остался запасным путём.

**Свои адаптеры — «частная» сеть, и держится она постоянно.** От типа сети
зависит, пустит ли сетевой экран входящие; сменить его нельзя, пока Windows
опознаёт сеть, а после смены адреса сеть может оказаться новой. Поэтому
проверка раз в 20 с, а не один вызов.

## 6. Грабли: на эти уже наступили

Самый ценный раздел. Каждый пункт стоил отладки.

### Кодировки и переводы строк

* **`start.bat` и `autostart.bat` — CP866 + CRLF.** При LF cmd разъезжается
  на `goto` и многострочных блоках: файл падает посреди выполнения.
  `chcp 65001` в начале файла **не решение** — cmd читает пакетный файл по
  байтовым смещениям, и смена кодировки по ходу ломает разбор строк с
  кириллицей.
* **`for /f` не выполняет команду, начинающуюся с кавычки.** cmd принимает
  первую кавычку за начало имени программы и ищет файл по всей строке.
  `for /f ... in ('"%NODE_EXE%" -e "..."')` молча возвращает пустой результат.
  Лечится префиксом `call`: строка начинается с буквы, а путь с пробелами
  внутри кавычек разбирается правильно.
* **`sed -i` в Git Bash срезает CR.** После массовой замены `.bat` молча
  перестаёт работать. Правьте пакетные файлы через Node или редактор.
* **В CP866 нет типографики.** «Ёлочки», длинное тире, многоточие обрывают
  `iconv` на первом же таком символе, и файл теряет хвост **молча**.
* **Скрипты PowerShell — UTF-8 с BOM.** Без BOM PowerShell 5.1 читает файл
  как ANSI и портит кириллицу.
* **PowerShell пишет в перенаправленный поток в кодировке консоли.**
  Перед выводом нужен `[Console]::OutputEncoding=[Text.Encoding]::UTF8`,
  иначе кириллица приходит мусором.

Всё перечисленное проверяется командой **`npm run check`** — прогоняйте её
после любых массовых правок.

### Ложные наблюдения

* **`Get-NetFirewallRule` без прав администратора падает с «Access is
  denied», а с `-ErrorAction SilentlyContinue` молча возвращает пустой
  список.** На этом был сделан неверный вывод «правила нет». Проверяйте
  через `netsh advfirewall firewall show rule name=all`.
* **`schtasks` печатает по-русски в кодировке консоли.** Регулярное
  выражение по такому выводу проверяет кодировку, а не задание. Используйте
  `Get-ScheduledTask` и структуру.
* **Сравнение рабочей копии с индексом git ничего не доказывает.** Так была
  «проверена» уже сломанная кодировка `start.bat`: подтвердилось лишь, что
  git её не менял.

### Гонки и ловушки исполнения

* **Опрос устройств заменял записи новыми объектами**, а освобождение
  держало ссылку на старый — правка уходила в объект, выброшенный из карты.
  Теперь записи обновляются **на месте**.
* **Список устройств собирается секундами** (перечисление COM/LPT/сети
  через PowerShell). Его нельзя применять как мгновенный снимок: состояние,
  выставленное после начала опроса, имеет приоритет (`stateStamp`).
* **`EventEmitter.emit('error')` без слушателя бросает необработанное
  исключение.** Занятый порт счётчика ронял всё приложение вместо отката.
  Для нефатальных событий используйте другое имя (в проекте — `'failed'`).
* **`child.kill('SIGTERM')` на Windows не даёт обработчикам отработать** —
  это `TerminateProcess`. Корректное завершение так не проверить; поднимайте
  узел в том же процессе и вызывайте `app.shutdown()`.

### Интерфейс

* **Недопустимое значение в свёрнутом разделе молча ломает всю форму.**
  Браузер отсчитывает шаг `<input type="number">` не от нуля, а от `min`:
  при `min="1" step="5"` допустимы 1, 6, 11, 16…, и обычные 30 секунд
  оказываются недопустимыми. Показать такое поле браузер не может, если оно
  внутри закрытого `<details>`, и просто отменяет отправку — обе кнопки
  диалога выглядят сломанными, в консоли пусто. Проверяется теперь командой
  `npm run check`; «Отмена» сделана обычной кнопкой, а «Сохранить»
  раскрывает раздел с ошибкой.
* **`returnValue` у `<dialog>` живёт между открытиями.** Закрытие по Esc
  оставляет прежнее значение, поэтому обработчик `close` обязан сверять его
  явно, а не полагаться на то, что диалог закрыли кнопкой.

### Круг доверия

* **Кругов у узла несколько, ключ выбирается по собеседнику.** Любой вызов
  к соседу подписывается ключом того круга, в котором сосед услышан
  (`peer.realm`). Общего «ключа узла» больше нет, и код, который его ищет,
  почти наверняка неверен.
* **Смена кругов не меняет содержимого анонса**, поэтому обычный
  `announce()` её не разошлёт — он молчит, когда объявлять нечего нового.
  Для этого есть `discovery.refresh()`, а покинутым кругам отправляется
  прощание (`farewell()`): иначе бывшие соседи держали бы узел в списке до
  таймаута, а это полторы минуты на медленном темпе.
* **Ключи не отдаются наружу никогда**, поэтому интерфейс не может прислать
  их обратно при правке названия. Пустой ключ у сети с известным `id` —
  это «оставить прежний».

* **Узел без ключа принимает любую подпись** — `verify()` при пустом ключе
  возвращает `true`. Поэтому защита «с ключом не видит без ключа» держится
  не на подписи, а на метке круга доверия, и проверять её обязаны ОБЕ
  стороны. В обмене каталогом это стоило отдельной ошибки: адрес узла без
  ключа, вписанный вручную, обходил разделение — тот получал карту всей
  сети. Теперь круг доверия выясняется запросом `ping` ДО отправки
  каталога.
* **Отправленное уже отправлено.** Проверка на приёмной стороне не спасает
  от утечки: тело запроса собеседник получил в любом случае. Всё, что
  нельзя показывать чужому узлу, проверяется до отправки, а не после.

### Проброс сетевой карты

* **Сборка моста выводит модальное окно ошибки — и ждёт.** `createbridge` на
  паре адаптеров включает в мост только первый, а на втором показывает
  «Возникла непредвиденная ошибка при настройке сетевого моста» с кнопкой
  «ОК». Команда не возвращается, пока окно не закроют; `CMIC_MASK_FLAG_NO_UI`
  оболочка здесь не соблюдает. Из приложения это выглядело как зависание
  сценария на две минуты. Лечится наблюдателем в `net-bridge.ps1`: он
  закрывает окна сообщений СВОЕГО процесса (узнаёт их по устройству — текст
  id 0xFFFF и кнопки, — а не по тексту), и второй адаптер досылается
  `addtobridge`, который поштучно срабатывает. Текст окна идёт в журнал.
* **`powershell -File` не разбирает массив через запятую**: `-Adapter a,b`
  приходит одной строкой `"a,b"`. Сценарий моста вызывается через
  `-Command`.
* **`devcon install` при первой установке драйвера выходит с кодом 1.** Печатает
  «Drivers installed successfully.», а код 1 означает «готово, просит
  перезагрузку». Приложение считало это отказом и отменяло занятие, хотя
  адаптер уже был создан: он оставался ничьим, а вторая попытка создавала
  ещё один. Перезагрузка на деле не нужна. Теперь успех — это появившийся
  адаптер, а не код возврата; так же и дальше: каждый шаг занятия проверяется
  по факту (адаптер открылся, вошёл в мост, канал ответил), с повторами там,
  где система отвечает не сразу.
* **`devcon install` переустанавливает драйвер на ВСЕХ экземплярах TAP.**
  Создание нового адаптера обрывает чтение у уже открытых («Операция была
  отменена»): у работающего проброса посредник падает, адаптеры OpenVPN
  переподключаются. С виртуальными адаптерами, которые заводят кнопкой, это
  стало недопустимо: теперь адаптер создаётся вызовами SetupAPI
  (`scripts/tap-device.ps1`, как tapctl из OpenVPN) — драйвер ставится
  только на новое устройство. Проверено: живой адаптер пользователя за все
  создания и удаления ни разу не мигнул. devcon — запасной путь.
* **Входящие к занявшему режет тип сети, а не проброс.** Приборы стенда «не
  видели» серверы клиента: новый адаптер — «общедоступная» сеть, и сетевой
  экран режет входящие. На машине стоял Kaspersky Endpoint Security, который
  зарегистрирован сетевым экраном вместо брандмауэра Windows (тот поэтому и
  «выключен» во всех профилях) и берёт тип сети у Windows. Разбор — в 8г.
* **Windows не объявляет назначенный адрес.** После `netsh ... set address`
  в провод не уходит ни одного ARP — ни пробы, ни объявления. Прибор, у
  которого адрес записан за MAC карты владельца, шлёт туда до истечения
  записи. Приложение объявляет адрес само (gratuitous ARP).
* **Драйвер TAP принимает только локальный MAC.** `NetworkAddress` вида
  `02AABBCC0001` берётся, `00FF4FA3CA99` и любой заводской — молча нет,
  адаптер остаётся со своим. Значение `MAC` (со старых версий, с
  двоеточиями) версия 9.27 не читает вовсе. MAC карты владельца занявшему не
  присвоить.
* **Категорию сети не сменить, пока Windows её опознаёт**: «Unable to set
  NetworkCategory on a network marked 'Identifying...'». Ставится после
  опознания (секунды), и держать её надо постоянно.
* **Адаптер моста — не всегда тот же.** Раньше мост создавался под прежним
  GUID, а в проверке 23 сентября мост проброса и мост коммутатора получили
  разные. Запись `Tcpip\Parameters\Interfaces\{GUID}` исчезает вместе с
  мостом. Поэтому GUID и прежние настройки запоминаются при каждой сборке.
* **MAC моста — MAC первого участника.** Проброс ставит первым свой TAP (MAC
  моста не совпадает с MAC карты), коммутатор — карту (компьютер остаётся в
  её сети под её MAC).
* **Отмена чтения TAP в .NET — это `OperationCanceledException`, а не код
  995.** NDIS ставит адаптер на паузу, когда меняется стек над ним: мост
  меняет состав, сетевой фильтр (видимо, Kaspersky) переподключается при
  смене профиля сети. Чтение отвечает «Операция была отменена» или
  «Параметр задан неверно» (87). Посредник выжидает до 8 с на том же
  дескрипторе — после паузы адаптер возвращается за ~100 мс. Если адаптер
  перезапущен (его включили в мост), дескриптор мёртв: посредник выходит, и
  `relayKeeper` поднимает его заново.
* **Трубу нельзя переключать посреди кадра.** Сокет рвётся на середине
  кадра; если просто переподключить поток, посредник прочтёт половину кадра
  как длину следующего и завершится. Поэтому поток режется по границам
  кадров (`FrameCutter`), и в посредника пишутся только целые кадры.
* **`spawnSync` в проверке останавливает весь проброс.** Посредники
  обслуживаются циклом событий того же процесса; синхронный `ping` на
  несколько секунд замораживал пересылку, и проверка честно показывала
  «ни одного кадра». Внешние команды в проверках — только асинхронно.

### Прочее

* **Любая страница в браузере — «локальный» клиент.** Простой POST с
  посторонней страницы на `127.0.0.1` браузер отправит без вопросов, а
  локальный доступ полный. Закрыто заголовком `X-NDS-UI` у изменяющих
  запросов интерфейса.
* **`new URL(import.meta.url).pathname` кодирует `~` в `%7E`.** В каталоге с
  короткими именами (`BOLSHA~1`) файл по такому пути не открывается —
  проверки падали на первой же записи журнала. `fileURLToPath`.
* **`--backend` не сохраняется в настройки** (в отличие от остальных ключей).
  Раньше сохранялся, и один запуск с `--backend mock` закреплял имитацию
  навсегда.
* **Второй интерфейс машины не годится как модель второго сегмента.**
  Виртуальный коммутатор Hyper-V (`vEthernet (Default Switch)`) молча
  глотает входящие TCP: брандмауэр Windows считает эту сеть публичной.
  Проверка падала с таймаутом по причине, не имеющей отношения к коду.
  Разделение сегментов проще изобразить **разными портами обнаружения**:
  узлы не слышат анонсов друг друга ровно так же, как если бы между ними
  стоял маршрутизатор, а HTTP при этом работает.
* **Подсеть виртуального коммутатора Hyper-V меняется после перезагрузки.**
  Зашитые в тест адреса протухают; берите их у `--networks`.
* **Замедление анонсов нельзя считать по каждому вызову `announce()`.**
  При старте и при публикации группы состояние меняется пачкой; если считать
  каждый такой вызов «тиком без изменений», узел уезжает на медленный темп
  за пару секунд — ровно противоположно замыслу. Замедляет только приход по
  таймеру (`reason === 'tick'`).
* **Два узла на одной машине** требуют разных `--api-port`,
  `--discovery-port`, `--traffic-port` и разных `NDS_HOME`.

## 7. Что НЕ проверено

Честный список. Всё это работает «по построению», но на живом железе не
запускалось.

* **Работа между настоящими сегментами сети.** Обмен каталогом проверен на
  одной машине: разделение изображалось разными портами обнаружения. Не
  проверено то, что даёт только настоящая топология: маршрут между
  подсетями, правила брандмауэра на 47812 и 47813, подключение устройства
  из чужого сегмента и учёт его трафика. Отдельно не проверялось поведение
  при обрыве связи между сегментами посреди занятого устройства.
* **Создание задания автозапуска в режиме S4U.** XML сформирован и проверен
  на разбор, но зарегистрировать задание можно только с правами
  администратора — на этой машине любой `schtasks /Create` отвечает
  «отказано в доступе» без повышения. Не проверено главное: что задание
  создаётся, что окно консоли действительно не появляется при входе и что
  откат на прежний режим срабатывает там, где S4U недоступен.
* **Приём вызова с адреса вне рабочей подсети.** На одной машине такого
  адреса взять неоткуда, поэтому правило «извне — только с общим ключом»
  проверено на уровне модулей, а не по сети.
* **Больше двух сегментов.** Цепочка из трёх подсетей (A↔B, B↔C) по
  построению не даст A увидеть C: пересказ ограничен одним шагом. Это
  осознанное решение, но на живой сети не проверялось — при трёх сегментах
  указывайте адреса так, чтобы каждая пара была связана напрямую.

* **Linux-бэкенд ни разу не запускался на настоящей машине.** Написан,
  проходит проверку синтаксиса, протестирован только через имитацию.
* **Реальный проброс через счётчик трафика.** Механика счётчика проверена
  на подставном `usbipd`; байты живого USB-устройства через него не ходили.
  Первый запуск стоит сделать на флешке или переходнике.
* **Автозапуск после настоящей перезагрузки.** Задание создаётся, свойства
  верные (`RunLevel Highest`, триггер входа), но перезагрузки не было.
* **Интерфейс вживую в браузере.** Вкладка «Сеть» снята в Edge без окна и
  посмотрена глазами (раздел 8г). Остальное прогнано тестами с подставным
  DOM; всплывает ли системное уведомление — не видел никто.
* **Вкладка «Сеть» на настоящей карте и между компьютерами** — см. 8г,
  «Не проверено».
* **Работа на втором компьютере.** Всё сетевое тестировалось между
  несколькими узлами на одной машине.
* **Проброс сетевой карты между двумя компьютерами** работает (проверил
  владелец проекта), но не проверены перенос настроек IP на настоящей карте,
  DHCP из сети владельца и скорость на реальном трафике.
* **Автозапуск на Linux** сделан пользовательским юнитом systemd. Для
  постоянно включённого стенда нужен системный юнит от root: `bind` без
  root не работает. Доработка не сделана.

## 8а. Проброс COM: разведка сделана

Решение принято — сначала сервер RFC 2217, драйвер клиента отдельно.
Ниже то, что проверено на живой машине и определяет устройство.

**Читать порт средствами Node нельзя.** `fs.open` на `\\.\COM1` работает,
запись проходит, `mode.com COM1: baud=…` настраивает порт — а вот `fs.read`
не возвращается **никогда**, пока не придут данные. Запрос висит в пуле
потоков libuv (по умолчанию их четыре), и несколько портов исчерпают его
целиком: встанут и файловые операции, и DNS, и crypto — всё приложение.
Поэтому читать порт в основном процессе нельзя ни в каком виде.

**Рабочий путь — .NET через PowerShell.** Проверено на COM1:

```powershell
$p = New-Object System.IO.Ports.SerialPort 'COM1',115200,'None',8,'One'
$p.ReadTimeout = 500
$p.Open()
```

Открывается, пишет, читает **с таймаутом** (поток не виснет), отдаёт
`CtsHolding`/`DsrHolding`/`CDHolding` — сигналы модема, без которых RFC 2217
неполон, — и перечисляет порты через `[System.IO.Ports.SerialPort]::GetPortNames()`.
`$p.BaseStream` — обычный `Stream`, его можно копировать в `[Console]::OpenStandardOutput()`
и обратно, то есть отдавать данные двоично-чисто через каналы процесса.

Отсюда устройство: **на каждый отданный порт — свой процесс-посредник**,
который блокируется вместо нас, а приложение говорит с ним по каналам и
держит TCP-сервер. Нативные модули и сборка по-прежнему не нужны — это
было главным ограничением проекта и остаётся им.

На Linux то же самое делается проще: `stty -F /dev/ttyS0 raw …` и отдельный
процесс `cat`; блокирующее чтение так же уезжает из основного процесса.

**Чего ещё нет.** Самого сервера RFC 2217, посредника, выдачи клиенту
адреса и порта, и признака `transport` у типа `com` (сейчас там `'none'`).

## 8б. Сетевой интерфейс: путь выбран, разведка сделана

Решения: адаптер должен появляться в «Диспетчере устройств» клиента;
идём **без Npcap** — через TAP-адаптер и встроенный мост Windows.

### Почему не Npcap

Его лицензия (проверено по тексту в `nmap/npcap`, редакция 2013–2025) прямо
запрещает распространение в составе другого продукта без платной OEM-лицензии.
Wireshark распространяет его по **именной оговорке**: он перечислен в лицензии
вместе с Nmap и Microsoft Defender for Identity. Сослаться на этот прецедент
нельзя. Бесплатная версия вдобавок ограничена пятью системами, и наше
приложение в список исключений не входит — то есть даже вариант «пусть
пользователь поставит сам» упирается в потолок.

### Что взято вместо него

`tap-windows6` 9.27.0, `dist.win10.zip` из релизов OpenVPN — 190 КБ:

* `tap0901.sys`, `tap0901.cat`, `OemVista.inf` — сам драйвер;
* `devcon.exe` — утилита Microsoft для создания экземпляров адаптера;
* `include/tap-windows.h` — коды IOCTL.

**Подпись — attestation, от Microsoft Windows Hardware Compatibility
Publisher.** Это лучший возможный вариант: такой драйвер загружается и при
включённой Memory Integrity, в отличие от com0com с его сертификатом 2012
года. Лицензия GPL-2.0 — та же схема оформления, что уже применена к
usbipd-win.

### Как это работает без захвата кадров

Инъекцией чужих MAC-адресов занимается ядро Windows, а не мы:

* **сервер** — TAP-адаптер, связанный встроенным мостом с физической картой;
  наш процесс читает и пишет только TAP;
* **клиент** — TAP-адаптер, наш процесс гоняет кадры между ним и TCP.

`bridge.sys` на проверенной машине **присутствует**, то есть мост в системе
есть. Создаётся он, однако, неудобно: командлета нет, `netsh bridge` умеет
только `show` и `set`. Остаётся COM-интерфейс либо один раз руками через
«Сетевые подключения → Настройка моста». Рассчитывать надо на второе.

### Чем открывать адаптер

Та же ловушка, что с COM, и даже хуже. Устройство `\\.\Global\{GUID}.tap`
открывается обычным `CreateFile`, но чтобы адаптер заработал, ему нужен
`TAP_WIN_IOCTL_SET_MEDIA_STATUS` — иначе он так и останется «сетевой кабель
не подключён». А `DeviceIoControl` из Node недоступен вовсе.

Проверенный механизм — P/Invoke через `Add-Type` в PowerShell. На машине
есть компилятор .NET 4.0.30319; `CreateFileW` и `DeviceIoControl` вызываются
и корректно возвращают коды Win32 (проба на `\\.\PhysicalDrive0` дала
ожидаемый код 5 — «отказано в доступе» без прав администратора).

Чтение кадров блокирует поток так же, как чтение COM-порта, поэтому и здесь
нужен **отдельный процесс-посредник**, а не работа в основном.

### Что с этим не так и требует решения

**Приложение станет похоже на вредоносное.** Компиляция кода в момент
выполнения плюс работа с драйвером через IOCTL плюс вставка произвольных
кадров в сеть — это ровно тот набор признаков, по которому срабатывает
эвристика антивирусов. У проекта есть правило «не делать того, что
неотличимо от вредоносного поведения», и здесь оно впервые вступает в
противоречие с задачей. Варианты: смириться и описать, либо собирать
посредник заранее и подписывать своим сертификатом — но это сборка, которой
в проекте нет, и сертификат, которого может не быть.

Остальное, что придётся решить: MTU, дублирование MAC-адреса в двух местах
сразу и что делает сервер со своей половиной трафика, пока карта занята.

### Что проверено на живой машине

Клиентская половина работает целиком. Проверено 21 сентября:

* `devcon install OemVista.inf tap0901` — код 0, адаптер создан;
* устройство `\\.\Global\{GUID}.tap` открывается;
* `GET_VERSION` → 9.27, `GET_MAC` → адрес адаптера;
* `SET_MEDIA_STATUS(1)` → адаптер переходит в **Up, 1 Gbps**;
* `WriteFile` с кадром ARP — 42 байта приняты драйвером.

**Права администратора нужны только на установку драйвера.** Само
устройство открывается и работает из-под обычного пользователя — значит,
процесс-реле повышения прав не потребует. Это лучше, чем ожидалось.

Проверка лежит в `scripts/probe-tap.ps1`, её можно повторить.

### Мост: компонент есть, привязка — только через INetCfg

Хорошая новость: `ms_bridge` («MAC-мост (Майкрософт)») **уже установлен**
в Windows — `netcfg -q ms_bridge` отвечает `is installed`. Ставить компонент
не нужно, и рискованный шаг с `netcfg -c s -i` отменяется.

Плохая новость: привязать к нему адаптер штатными средствами нельзя.
`Get-NetAdapterBinding` компонента `ms_bridge` не показывает ни на одном
адаптере — мост это не обычная привязка NDIS, а отдельный минипорт, к
которому адаптеры присоединяются через **INetCfg**. Тот самый COM-интерфейс,
которым пользуется панель управления. Другого пути не нашлось:
`netsh bridge` умеет только `show` и `set`

### Что нашлось попутно и меняет картину

* **Npcap на машине уже стоит** (`insecure_npcap` в списке компонентов) —
  видимо, с Wireshark. Для разработки и проверок это удобно; на решение
  не распространять его в составе продукта не влияет.
* Там же `kl_klim6` — фильтр Касперского, и `vmware_bridge`. Машина
  насыщена сетевыми фильтрами; это стоит учитывать, когда что-то не ходит.
* В системе есть драйвер **USB Wi-Fi адаптера** (`usb\vid_0bda&pid_818b`,
  Realtek RTL8192EU). Любой USB-адаптер пробрасывается уже сегодня, без
  единой строки нового кода, — на время разработки это рабочий обходной путь.

### Осталось непроверенным

Устарело — см. раздел 8в: чтение кадров, мост и передача между TAP сделаны
и проверены; не проверена только работа между двумя компьютерами.

## 8в. Проброс сети: что сделано и где упёрлось

### Работает и проверено

* `scripts/tap-relay.ps1` — посредник: поднимает адаптер, гоняет кадры;
* `src/net/tapRelay.js` — сторона Node, разбор потока, счётчики;
* `src/net/tapLink.js` — канал L2 по TCP.

На живом адаптере: 203 кадра за 8 секунд от системы, 41 КБ через TCP,
в потоке ARP, IPv6, LLDP, IPv4. Обрыв связи не роняет посредника, адаптер
остаётся поднятым, переподключение проходит.

Формат обмена с посредником и формат на проводе одинаковы, поэтому кадры
не попадают в JavaScript вовсе — Node только соединяет трубы.

### Мост: почему не работают очевидные пути

Разгадка в `%SystemRoot%\INF\netbrdg.inf`:

```
Characteristics=0x40000   ; NCF_LW_FILTER
```

**MAC-мост в Windows 10 — это NDIS-фильтр, а не устройство и не служба.**
Отсюда следует всё остальное, и все четыре документированных пути отпадают
по одной и той же причине.

| Путь | Что ответил | Почему |
|---|---|---|
| `netsh bridge` | умеет только `show` и `set` | создания нет в принципе |
| `Enable-NetAdapterBinding -ComponentID ms_bridge` | объект WMI не найден | фильтр не выставлен в `MSFT_NetAdapterBindingSettingData` |
| `INetCfgComponentBindings::BindTo` | S_FALSE | фильтры привязываются не так |
| `INetCfgClassSetup::Install` | 0x800F0208 | «элемент не зарегистрирован как устройство» — он и не устройство |

Проверено с взятой блокировкой записи и без неё, на всех шестнадцати
адаптерах системы. `ms_bridge` не виден даже в `Get-NetAdapterBinding -AllBindings`.

Версия «мешает Hyper-V» проверена и не подтвердилась: протокол
виртуального коммутатора (`vms_pp`) не привязан ни к одной карте, а
Default Switch — коммутатор внутренний и физическую карту не занимает.

### Идентификаторы интерфейсов INetCfg

В справочниках указаны неверно; подобраны опросом самих объектов
(`QueryInterface` по диапазону). Компонентные отличаются, классовые — нет:

| Интерфейс | Идентификатор |
|---|---|
| INetCfg | C0E8AE93-306E-11D1-AACF-00805FC1270E |
| IEnumNetCfgComponent | **C0E8AE92** (а не 9B) |
| INetCfgComponent | C0E8AE99 |
| INetCfgComponentBindings | **C0E8AE9E** (а не 9D) |
| INetCfgLock | C0E8AE9F |
| INetCfgClass | C0E8AE97 |
| INetCfgClassSetup | C0E8AE9D |

Ещё две особенности: перечислитель не отдаёт массив интерфейсных
указателей — запрашивать надо строго по одному; блокировку записи надо
брать **до** `Initialize`, иначе конфигурация открывается только на чтение.

Всё это в `scripts/probe-netcfg.ps1` — скрипт только читает.

### Как мост всё-таки создаётся

Все четыре пути выше искали мост среди устройств и служб. А он — пункт
меню. Папка «Сетевые подключения» — обычная папка оболочки
(`CSIDL_CONNECTIONS` = 0x31), её элементы отдают `IContextMenu`, и команды
там свои:

| Внутреннее имя | Что делает | Сколько адаптеров выделено |
|---|---|---|
| `createbridge` | создаёт мост | два и больше |
| `addtobridge` | добавляет в существующий мост | один |
| `removefrombridge` | выводит из моста | один |

Внутренние имена читаются через `GetCommandString(GCS_VERBW)` и от языка
Windows не зависят — искать пункт по надписи не нужно. Права нужны
административные, повышение обычное, через `-Verb RunAs`.

Всё это в `scripts/net-bridge.ps1`; действия `state`, `verbs`, `bridge`,
`unbridge`.

Три грабли, каждая стоила отдельного разбора:

* **Массивы в `IShellFolder` объявлять с `[MarshalAs(UnmanagedType.LPArray)]`.**
  В COM-интерфейсе массив по умолчанию едет как SAFEARRAY, и `GetUIObjectOf`
  роняет процесс нарушением доступа.
* **`rgfReserved` передавать указателем на настоящую память**, не нулём.
* **`CMIC_MASK_FLAG_NO_UI` не ставить на `delete`.** Команда вернёт S_OK и
  не сделает ничего: подавленный вопрос считается отказом. Мост и не надо
  удалять отдельно — он исчезает сам, когда из него выходит последний
  участник.

Проверено на живой машине: `createbridge` на паре «TAP + Ethernet» создаёт
мост с обоими участниками, `unbridge` возвращает всё как было.

### Как это собрано в приложении (23 сентября)

```
ВЛАДЕЛЕЦ:  карта ═ мост Windows ═ TAP ⇄ посредник ⇄ канал :47814 ─┐
ЗАНЯВШИЙ:                        TAP ⇄ посредник ⇄ канал ◀────────┘
```

* **Занятие** (`shareManager.claim` → `hub.bind` → `netShare.lend`):
  свободный TAP владельца (или новый), переименование в «NDS мост — <карта>»,
  мост, снятие IP с адаптера моста, посредник, сеанс канала с пропуском.
  Ответ на занятие несёт `links: [{ deviceId, port, token }]`.
* **Клиент** (`attachManager` → `netShare.borrow`): свой TAP (за целью
  закрепляется «её» адаптер — с теми же настройками IP), имя
  «<карта> на <владелец>», посредник, подключение к каналу. Связь
  восстанавливается сама; отказ владельца (пропуск больше не действует)
  прекращает попытки.
* **Освобождение**: держатель отключается сразу, мост разбирается следом
  (5–6 с), не задерживая ответ. Следующая сборка встаёт в очередь за
  разборкой.
* **Пропуск**: 32 случайных байта на каждое занятие, умирает вместе с ним;
  канал пускает только с адреса, с которого занимали. Кадры не шифруются —
  как и USB/IP.
* **Одна карта на владельца одновременно**: мост в Windows один, вторая
  карта слила бы две сети в одну. Чужой мост (собранный человеком) —
  отказ с объяснением.
* **Сбой посреди выдачи**: отданная карта пишется в `netLent` до сборки
  моста; при следующем запуске мост по этой записи разбирается.
* **Наши адаптеры** — только созданные приложением (`tapAdapters` в
  настройках): OpenVPN ставит тот же драйвер, и отличить его адаптер иначе
  нельзя.
* **Скорость** считает посредник владельца; держателю она приходит в ответе
  на heartbeat, как у USB.
* **Настройки IP карты переезжают к занявшему.** Владелец до сборки моста
  читает их из реестра (`Tcpip\Parameters\Interfaces\{GUID}`: пока карта в
  мосту, стек IP её не видит, а реестр — видит) и отдаёт в ответе на
  занятие. Клиент ставит своему адаптеру то же: DHCP или адрес, маску, шлюз,
  DNS — после подключения канала, чтобы объявление адреса дошло до
  устройств стенда. Метрика адаптера клиента — 400: шлюз и DNS стенда не
  перехватывают его собственный выход в сеть. После освобождения адаптер
  возвращается к DHCP без ручных адресов. Нужны права администратора; без них
  адаптер работает, но адрес надо задать вручную — интерфейс так и пишет.
* **Ход занятия виден.** Запись занятия несёт `stage` («владелец готовит
  карту», «адаптер поднимается», «подключение к карте владельца», «перенос
  настроек IP»), у владельца карта на время сборки моста помечена
  «готовится к выдаче». При сбое в сообщении — шаг, на котором сорвалось.

### Проверено 23 сентября

Без прав администратора: канал (29 проверок — пропуск, чужой адрес, мусор
вместо приветствия, обрыв посреди кадра, встречный напор, замена

## 8г. Сеть компьютера: коммутаторы, виртуальные адаптеры, настройки (23 сентября)

### С чего началось

Проверяя проброс между двумя компьютерами (карта `Ethernet 2` второго
компьютера у этой машины), владелец проекта сообщил:

* на мосту у владельца нет IP, и поменять его нельзя — ни у моста, ни у карт
  в нём;
* свои настройки клиент меняет у себя, а у владельца ничего не меняется;
* **устройства сети владельца не видят серверов, запущенных у клиента**, даже
  после добавления нужных адресов — «может, устройствам нужны разные MAC»;
* нужна настройка сети в интерфейсе, как в утилите VirtualNics, но без
  Hyper-V: коммутаторы, адаптеры, карта связей, настройки — и с другого
  компьютера по паролю; настройки должен уметь менять и клиент, а после
  освобождения у владельца всё должно вернуться как было.

### Почему устройства стенда не видели клиента

Прежняя проверка пинговала стенд с клиента, то есть проверяла только связь,
которую начинает клиент. Связь, начатую прибором, не проверял никто. Стенд
`t-l2`: «прибор» на «проводе» сам шлёт ARP, ping и TCP SYN к серверу на
адаптере клиента.

| Что | Результат |
|---|---|
| ARP прибора «кто адрес клиента» | ответ за 1 мс — кадры идут в обе стороны |
| TCP SYN прибора к серверу клиента (node.exe) | SYN-ACK — соединение открывается |
| ping прибора к клиенту | **ответа нет**, хотя брандмауэр Windows выключен |
| то же после перевода сети адаптера в «частную» | ответов 2 из 3 |
| прибор со старой записью ARP (адрес → MAC карты) | **не достаёт** |
| ARP, разосланный Windows при назначении адреса | **ни одного** |
| MAC карты на адаптере клиента | драйвер не принял (грабли, раздел 6) |

Сам проброс L2 работает в обе стороны; мешает то, что вокруг.

1. **Тип сети.** Новый адаптер Windows относит к общедоступной сети. На
   машине стоит Kaspersky Endpoint Security; он зарегистрирован сетевым
   экраном вместо брандмауэра Windows и берёт тип сети у неё: входящий
   ping пошёл сразу после `Set-NetConnectionProfile -NetworkCategory
   Private`. У живого адаптера
   занятой карты категория была Public. TCP к node.exe проходил —
   видимо, node у KES в доверенных; серверы пользователя, скорее всего,
   резались.
2. **Старые записи ARP.** Адрес у клиента раньше был адресом карты
   владельца, прибор шлёт на её MAC, пока запись не устареет, а Windows
   новый адрес не объявляет.

Что сделано:

* свои адаптеры (взятые карты и виртуальные) — «частная» сеть, и
  приложение держит её постоянно (`ensureCategories` раз в 20 с); на
  карточке видно и переключается;
* объявление адреса (gratuitous ARP) от имени адаптера: у клиента — через
  канал (`LinkClient.inject`), у виртуального — через коммутатор
  (`VSwitch.inject`); трижды (0, 1, 3 с) на каждый новый адрес, в том числе
  заданный в свойствах Windows (`os.networkInterfaces()` раз в 3–4 с);
* у владельца при освобождении — объявление адреса карты от её MAC, пока
  мост ещё собран: приборы сразу возвращаются к карте;
* сторонний сетевой экран виден на вкладке «Сеть» с подсказкой, где в нём
  статус сети.

### Как устроено

```
                                                     ┌─ виртуальный адаптер A (TAP, свой MAC и IP)
 карта ═ мост Windows ═ TAP «выход» ⇄ коммутатор ─────┼─ виртуальный адаптер B
            ║                        (Node, L2)       └─ …
            ╠═ адаптер «Сетевой мост» — сам компьютер (адрес карты)
            ╚═ TAP проброса ⇄ канал ⇄ занявший (если карту отдали)
```

* `src/net/vswitch.js` — обучающийся коммутатор: MAC → порт, рассылка
  неизвестных и групповых, старение 5 мин; порт с очередью больше 1 МБ
  теряет кадры, а не тормозит остальных.
* `src/net/relayKeeper.js` — посредник, который поднимается заново
  (вынесен из `netShare.js`), и включение посредника портом коммутатора.
* `src/core/netManager.js` — коммутаторы, виртуальные адаптеры, правки,
  карта. Операции строго по одной; записи — `netSwitches` и `tapAdapters`
  с ролями `vnic` и `uplink`.
* `src/net/adapters.js` — опись одним вызовом PowerShell (~1,7 с): привязки
  `ms_tcpip` и `ms_implat`, адреса, профиль сети, реестр, маршрут по
  умолчанию; сторонние экраны — из `root/SecurityCenter2`.
* `scripts/tap-device.ps1` — создание и удаление TAP по одному (SetupAPI).
* `src/ui/net.js` — вкладка: полосы и колонки (чужая карта → карты →
  мост и коммутаторы → интерфейсы → другие компьютеры), рёбра в SVG,
  карточки, диалоги.

Решения:

* **Внешний коммутатор — это мост Windows, наш TAP и программный
  коммутатор.** Мост даёт компьютеру один интерфейс — адаптер моста: TAP,
  включённый в мост, теряет свой стек IP. Поэтому виртуальные адаптеры в мост
  не включаются, а сидят на программном коммутаторе, выход которого — один
  TAP в мосту. Мост в Windows один, значит, и внешний коммутатор один.
* **При создании коммутатора адрес карты переезжает на мост** (как у
  Hyper-V), при удалении мосту возвращаются прежние настройки, а карта свои
  получает сама: её запись в реестре не трогается.
* **Проброс карты из коммутатора — через общий мост.** В мост добавляется
  только TAP проброса, IP моста не трогается, адрес карты клиенту не
  переносится (он занят владельцем): клиент получает примечание `ipNote` и
  задаёт адрес сам.
* **У виртуальных адаптеров выключена проверка адреса на дубликат**
  (`dadtransmits=0`): несколько адаптеров компьютера в одном сегменте иначе
  гасят друг другу адреса (урок VirtualNics).
* **Бронь: держатель меняет настройки карты у владельца** (`/api/v1/peer/net-ip`).
  Прежние запоминаются в `netRestore` — в файле, не в памяти — и
  возвращаются при освобождении, при выходе и при запуске после сбоя. У
  проброшенной карты держатель меняет свой адаптер.
* **На мосту отданной карты владелец может включить IP** и задать свой
  адрес; при освобождении мосту возвращаются прежние настройки (снимок в
  `netLent.bridge` — на случай сбоя).
* **Нельзя:** рабочую карту — в мост и менять ей адрес (оборвётся связь и с
  узлами, и с тем, кто управляет через браузер); Wi-Fi — в мост; адрес

## 8д. Адаптеры, созданные не приложением (24 сентября)

### С чего началось

Владелец проекта: в меню нельзя удалить или изменить уже существующие
адаптеры, созданные не нашей программой, и нельзя добавить для них
коммутатор — соединить их в сеть. До этого у чужих адаптеров была одна
кнопка — «Настройки IP»; чужие TAP сознательно не трогались вовсе (OpenVPN
ставит тот же драйвер).

### Как устроено

* **Одно правило прав** — `NetManager._rights(a, role, ctx)`: что можно
  сделать с адаптером (`can`) и почему нельзя остального (`why`, `why.manage`
  — отказ во всём). По нему рисуются кнопки на карте, и по нему же, по свежей
  описи, проверяют себя сами операции — расхождения между кнопкой и отказом
  сервера быть не может.
* **`updateAdapter(guid, { name, mac, enabled, switchId })`** — любой
  адаптер; прежний `updateVnic` стал его псевдонимом. `deleteAdapter` —
  так же вместо `deleteVnic`.
* **Чужой TAP — портом коммутатора.** Запись в `tapAdapters` с
  `role: 'vnic', adopted: true`: дальше он живёт как виртуальный адаптер
  (порт, объявление адресов, тип сети «частная»). Отключили от коммутатора
  («Отпустить», `switchId: null`), удалили коммутатор или запись осталась
  без коммутатора при запуске — запись убирается, адаптер свободен.
* **Прочие адаптеры — мостом**, как карта (`_nicProblem` больше не требует
  физической карты). Hyper-V — нет: у него свой коммутатор.
* **Опись** (`adapters.js`) узнаёт: поддерживает ли драйвер смену MAC
  (свойство `NetworkAddress` на вкладке «Дополнительно» — `macSettable`),
  задан ли MAC вместо заводского (`macCustom`), адаптер ли это Hyper-V
  (`ROOT\VMS_MP\…`), программное ли устройство (`ROOT\…` — `software`).
* **Операции** (`tapAdapters.js`): `setAdapterMac` (то же значение
  `NetworkAddress` в ключе драйвера, что у TAP; правило «только локальный
  MAC» — лишь для TAP), `removeAdapter` (DIF_REMOVE по идентификатору
  экземпляра, тем же `tap-device.ps1`), `setAdapterEnabled`,
  `renameAdapter(…, { explain: true })` — с причиной отказа. Переименование
  идёт по конвейеру, а не `-Name`: `-Name` понимает шаблоны, и имя со
  скобками `[ ]` нашло бы не тот адаптер.

Что нельзя и почему:

| Что | Почему |
|---|---|
| рабочая карта — всё, кроме типа сети | приложение знает её по имени; отключить или перезапустить (MAC) — оборвать связь с узлами и со страницей |
| занятая карта — всё | она у держателя |
| опубликованная карта — имя | имя карты — её адрес в каталоге (`net:<имя>`): публикация и группы потерялись бы |
| физическая карта — удалить | Windows найдёт её снова при опросе оборудования; её отключают |
| Hyper-V — удалить, MAC, в мост | этим распоряжается Hyper-V (Диспетчер Hyper-V) |
| в мосту — отключить, MAC, удалить | сначала вывести из коммутатора: MAC моста — MAC первой карты |
| порт коммутатора — отключить | выводится из сети отключением от коммутатора |
| служебные адаптеры приложения | живут и удаляются вместе с коммутатором или пробросом |

### Грабли

* **TAP открывается только одной программой.** Проверено: адаптер, который
  держит работающее приложение, второй посредник не открывает («не найден
  или занят другой программой»). Поэтому чужой TAP, которым пользуется
  OpenVPN, подключиться не может — и не крадёт у него кадры; отказ приходит
  через ~12 с (пять попыток открыть) с объяснением, запись убирается.
* **`HardwareInterface` врёт у адаптера замыкания.** KM-TEST
  (`ROOT\NET\…`) называет себя оборудованием. Физической картой считается
  только не программное устройство.

## 9. Что дальше

По убыванию пользы:

1. **Проверить на двух компьютерах** новую версию: входящие к занявшему
   (тип сети, объявление адреса), перенос настроек IP, коммутатор на
   настоящей карте, вкладку «Сеть» с другого компьютера по паролю
   (раздел 8г); смену MAC у настоящей карты и адаптеры настоящих OpenVPN и
   VirtualBox (раздел 8д).
2. **Перенести тесты в репозиторий** — без них любая правка рискованна.
   Отдельно: у `build-release.mjs` нет проверки, что собранный комплект
   запускается. Сейчас это делается руками — распаковать, убрать Node из
   `PATH`, выполнить `start.bat --doctor`.
3. **Транспорт для COM** — RFC 2217 плюс драйвер виртуального порта у
   клиента. Самая крупная и самая востребованная задача.
4. **Служба Windows** — чтобы стенд раздавал устройства без входа в систему.
   Ставить через подписанный `winsw` (не `nssm` — он без подписи).
   Осторожно с сетевыми картами: мост собирается командой папки «Сетевые
   подключения», то есть оболочкой, а из службы (сеанс 0, без рабочего
   стола) это не проверялось и может не работать.
5. **Системный юнит systemd** для Linux-стенда.
6. **Очередь ожидания** на занятое устройство вместо отказа.
