# Самообновление и установщик

Когда кто-то в сети получает новую версию, остальные узлы видят её,
скачивают друг у друга по очереди, проверяют подпись и тихо перезапускаются.
Не запустилась — возвращаются к прежней. Решения этого документа прошли
архитектурное ревью; ниже — что и почему сделано так.

## Главное правило: доверие — только подпись

Адрес соседа, общий ключ круга, «он же наш» ничего не доказывают. Подпись
HMAC на запросах между узлами покрывает только тело: у любого `GET` оно
пустое, то есть подпись постоянна, а в открытом круге её нет вовсе. Поэтому
всё, что пришло по сети, считается чужим, пока не пройдёт проверку подписи
релиза (Ed25519), и подпись проверяется до того, как что-либо скачано или
распаковано.

Что отвергается: неизвестный ключ, не тот канал, неверная подпись, версия не
новее установленной (откат по сети запрещён), архив с размером или суммой не
из подписанного манифеста, лишний или изменённый файл, путь с `..`, диском,
зарезервированным именем Windows, символическая ссылка, «gzip-бомба».

## Что где лежит

```
<база>/                       Program Files\NetDeviceShare  или каталог комплекта
  node.exe, start.bat, autostart.bat      меняются только установщиком
  launcher/                   лаунчер и библиотека — корень доверия, вшитые ключи
  installers/                 драйверы и Node (общие для всех версий)
  app/<версия>/               код версии + release.json + release.sig
  releases/<версия>/          подписанный архив (источник восстановления и раздачи)
  download/                   копия установщика для раздачи соседям
  installed.json              признак «поставлено установщиком» и каталог данных
<данные>/                     ProgramData\NetDeviceShare (установка) или %APPDATA%\net-device-share (комплект)
  config.json                 настройки (ключи, nodeId)
  update/state.json           current, previous, pending, bad, highestInstalled
```

Код приложения лежит там, куда обычному пользователю писать нельзя: оно
работает с правами администратора, и иначе любой процесс пользователя
получил бы эти права, подменив файл. Данные в ProgramData закрыты ACL для
SYSTEM и администраторов — в них ключи сети и пароль интерфейса.

Версия живёт в одном месте — `package.json`. `app.version` читается оттуда,
рассинхрона нет (он дал бы бесконечный цикл «новее себя»).

## Релиз

Файлы `release.json` (манифест: версия, канал, ключ, сумма и размер архива,
файлы с суммами, совместимость), `release.sig` (подпись Ed25519 над точными
байтами манифеста) и `payload.tar.gz` (файлы версии, ustar, воспроизводимо).
Вручную переносится одним файлом `.ndsupd`.

В нагрузку входят `src/`, `docs/`, `package.json`, `README.md`, `LICENSE` и
`.ps1` скрипты. Не входят `node.exe`, драйверы, `start.bat`, лаунчер: их
меняет только установщик. Если версии нужен более новый лаунчер или Node,
в манифесте `compat.minLauncher`/`minNode`, и узел отвечает «нужен
установщик», а не пытается обновиться.

## Лаунчер (`launcher/supervisor.mjs`)

Запускается из `start.bat`, `autostart.bat` и задания автозапуска, а не
приложение напрямую. Он: выбирает версию и проверяет её целостность
(подпись и суммы всех файлов); повреждённую восстанавливает из
`releases/<версия>/`; запускает приложение и перезапускает при падении
(5 с, 30 с, 2 мин); по коду выхода `75` переключается на другую версию без
паузы.

**Пробный запуск.** Новая версия — `pending`. Перед запуском снимается копия
`config.json`. Версия подтверждается сообщением `healthy` от приложения (через
IPC, через 45 с без необработанных исключений). Не подтвердила за 120 с или
упала — вторая попытка, после неё откат: версия помечается плохой на этом
узле, `config.json` возвращается из копии, продолжается предыдущая версия.
Подтвердила — `previous` ← `current`, всё старше удаляется.

Ctrl+C получают и лаунчер, и приложение: лаунчер дожидается выхода приложения
и выходит сам, не перезапуская. Остановка из другой консоли —
`supervisor.mjs --stop` (флаг-файл; на Windows мягкого сигнала нет).

Запуск «из исходников» (нет `app/`) идёт без обновления: менять каталог
разработчика нельзя.

Команды: `--install-release <файл.ndsupd> [--allow-downgrade]`, `--adopt`
(принять версию, привезённую установщиком), `--verify`, `--status`, `--stop`.

## Раздача по сети

Протокол — в [PROTOCOL.md](PROTOCOL.md). Кратко: узел видит у соседа версию
новее (`version` уже есть в анонсе и каталоге), берёт у него подписанный
манифест, занимает слот на скачивание, качает архив, проверяет и раскладывает
рядом с текущей версией. Источник держит 2 слота (настройка `updateSlots`),
один слот на адрес; лишним отвечает `503 busy` со случайным `Retry-After`.
Скачавший узел сразу становится источником, хотя ещё не перезапущен: поэтому
спрашиваются и узлы, у которых версия выглядит старой. Порядок источников для
каждого узла свой (хеш от пары узлов и версии), своя подсеть раньше узлов из
других сетей (те — только если в подсети источника нет 10 минут).

Узел, отдавший мусор или оборвавший передачу, не используется час.

## Когда безопасно перезапускаться

Перезапуск сбрасывает чужие аренды наших устройств (занятость живёт в памяти),
обрывает наши подключения, возвращает отданную сетевую карту. Узел ждёт, пока:
нет чужих аренд, нет своих подключений, не отдана карта, не идёт установка
компонентов, никто не качает с него обновление. Причины ожидания показаны в
интерфейсе.

**Очередь.** Без координатора: узел, получивший версию раньше всех (источник),
перезапускается первым и работает `updateCanaryMinutes` (10) как «канарейка» —
если версия плохая, откат случится у одного узла. Затем остальные по очереди с
шагом `updateWaveStepSec` (30 с); место определяет хеш от идентификатора узла и
версии, у каждой версии порядок свой.

Режимы (`updateMode`): `auto`, `ask` (качает, но ставит после разрешения в
интерфейсе), `off`. По умолчанию: у установленного приложения `auto`
(есть `installed.json`), у переносимого комплекта `ask`.

## Ключи

Ed25519, два с первого дня: `k1` — рабочий, `k2` — запасной (закрытую часть
унести с компьютера сборки на отдельный носитель). Открытые ключи вшиты в
`launcher/lib/keys.js`; закрытые лежат вне репозитория
(`~/.net-device-share-signing/`, путь — `NDS_SIGNING_KEY`, пароль —
`NDS_SIGNING_PASS`). Создание: `node scripts/release-keygen.mjs --id k1`.

Список ключей — часть лаунчера, и сетевое обновление его заменить не может
(иначе компрометация одного обновления отдала бы корень доверия). Ротация:
выпуск, подписанный `k1`, затем установщик с `{k2, k3}`. Потерян `k1` — выпуск,
подписанный `k2`, и установщик без `k1`.

Тестовый ключ (`NDS_UPDATE_TEST_KEY=<путь к открытому ключу>`) вправе
подписывать только канал `test`; включение пишется в журнал. Он нужен для
проверок на одной машине и в рабочей сборке не используется.

## Как выпустить версию

1. Поднять `version` в `package.json`.
2. `npm test` — проверки лаунчера, раздачи и сквозная (три узла на одной
   машине).
3. `node scripts/build-update.mjs` — подписанный релиз в `dist/release/<версия>/`
   (`.ndsupd`).
4. `npm run build` — переносимый комплект (если ключ есть, в раскладке с
   лаунчером; `--legacy-layout` — старая раскладка без обновления).
5. `npm run build:installer` — установщик (нужен Inno Setup 6).
6. Первый узел получает версию из `.ndsupd`:
   `node.exe launcher\supervisor.mjs --install-release файл.ndsupd` — и перезапускается.
   Остальные подтянут её сами.

Узлы версий до 2.1.0 не умеют обновляться: первую версию с механизмом
придётся поставить на каждый узел руками (установщиком или комплектом).

## Проверка на одной машине

`node --test test/update/*.test.mjs`. Сквозной тест поднимает три настоящих
узла (код из репозитория под лаунчером, тестовый ключ, порт обнаружения 47911,
`--backend mock`), проверяет раздачу, пробный запуск и подтверждение.

## Чего здесь нет и что сделано осознанно

- **Нет принудительного перезапуска по таймеру** и окна обслуживания: занятый
  узел ждёт сколько нужно. Есть кнопка «Перезапустить сейчас».
- **Обновление Node.js и драйверов** по сети не делается — только установщиком.
- **Подпись самого установщика** (Authenticode) не настроена: без сертификата
  SmartScreen предупредит. Страница `/download` показывает SHA-256 файла.
- **Правка подписи RPC** (метод, путь, время и nonce в подпись) и запрет
  `usbipdPath` из удалённых настроек (запуск файла с правами администратора по
  паролю интерфейса) — отдельными задачами и выпусками, с учётом
  совместимости в смешанной сети.
- Установщик Windows (`installer/nds.iss.tpl`) **не собирался** на этой
  машине (нет Inno Setup); шаблон написан по документации и требует
  проверки на чистой виртуальной машине.
