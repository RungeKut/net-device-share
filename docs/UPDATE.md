# Самообновление и установщик

Когда кто-то в сети получает новую версию, остальные узлы видят её,
скачивают друг у друга по очереди, проверяют подпись и тихо перезапускаются.
Не запустилась — возвращаются к прежней. Решения этого документа прошли
архитектурное ревью; ниже — что и почему сделано так.

## Главное правило: доверие — только подпись

Адрес соседа, общий ключ круга, «он же наш» ничего не доказывают. Подпись
HMAC на запросах между узлами покрывает только тело: у любого `GET` оно
пустое, то есть подпись постоянна, а в открытом круге её нет вовсе. Поэтому
всё, что пришло по сети, считается чужим, пока не пройдёт проверку подписи
релиза (Ed25519), и подпись проверяется до того, как что-либо скачано или
распаковано.

Что отвергается: неизвестный ключ, не тот канал, неверная подпись, версия не
новее установленной (откат по сети запрещён), архив с размером или суммой не
из подписанного манифеста, лишний или изменённый файл, путь с `..`, диском,
зарезервированным именем Windows, символическая ссылка, «gzip-бомба».

## Что где лежит

```
<база>/                       Program Files\NetDeviceShare  или каталог комплекта
  node.exe, start.bat, autostart.bat      меняются только установщиком
  launcher/                   лаунчер и библиотека — корень доверия, вшитые ключи
  installers/                 драйверы и Node (общие для всех версий)
  app/<версия>/               код версии + release.json + release.sig
  releases/<версия>/          подписанный архив (источник восстановления и раздачи)
  download/                   копия установщика для раздачи соседям
  installed.json              признак «поставлено установщиком» и каталог данных
<данные>/                     ProgramData\NetDeviceShare (установка) или %APPDATA%\net-device-share (комплект)
  config.json                 настройки (ключи, nodeId)
  update/state.json           current, previous, pending, bad, highestInstalled
```

Код приложения лежит там, куда обычному пользователю писать нельзя: оно
работает с правами администратора, и иначе любой процесс пользователя
получил бы эти права, подменив файл. Данные в ProgramData закрыты ACL для
SYSTEM и администраторов — в них ключи сети и пароль интерфейса.

Версия живёт в одном месте — `package.json`. `app.version` читается оттуда,
рассинхрона нет (он дал бы бесконечный цикл «новее себя»).

## Релиз

Файлы `release.json` (манифест: версия, канал, ключ, сумма и размер архива,
файлы с суммами, совместимость), `release.sig` (подпись Ed25519 над точными
байтами манифеста) и `payload.tar.gz` (файлы версии, ustar, воспроизводимо).
Вручную переносится одним файлом `.ndsupd`.

В нагрузку входят `src/`, `docs/`, `package.json`, `README.md`, `LICENSE` и
`.ps1` скрипты. Не входят `node.exe`, драйверы, `start.bat`, лаунчер: их
меняет только установщик. Если версии нужен более новый лаунчер или Node,
в манифесте `compat.minLauncher`/`minNode`, и узел отвечает «нужен
установщик», а не пытается обновиться. В интерфейсе тогда появляется кнопка
«Скачать установщик у „Имя узла“» со ссылкой на `/download` того соседа, который
уже работает на этой версии и раздаёт установщик (проверяется запросом); если
такого нет — подсказка взять установщик у администратора. Установщик не
запускается сам: это исполняемый файл с правами администратора, а его подлинность
подписью релиза не подтвердить (он содержит этот релиз).

## Лаунчер (`launcher/supervisor.mjs`)

Запускается из `start.bat`, `autostart.bat` и задания автозапуска, а не
приложение напрямую. Он: выбирает версию и проверяет её целостность
(подпись и суммы всех файлов); повреждённую восстанавливает из
`releases/<версия>/`; запускает приложение и перезапускает при падении
(5 с, 30 с, 2 мин); по коду выхода `75` переключается на другую версию без
паузы.

**Пробный запуск.** Новая версия — `pending`. Перед запуском снимается копия
`config.json`. Версия подтверждается сообщением `healthy` от приложения (через
IPC, через 45 с без необработанных исключений). Не подтвердила за 120 с или
упала — вторая попытка, после неё откат: версия помечается плохой на этом
узле, `config.json` возвращается из копии, продолжается предыдущая версия.
Подтвердила — `previous` ← `current`, всё старше удаляется.

Ctrl+C получают и лаунчер, и приложение: лаунчер дожидается выхода приложения
и выходит сам, не перезапуская. Остановка из другой консоли —
`supervisor.mjs --stop` (флаг-файл; на Windows мягкого сигнала нет).

Запуск «из исходников» (нет `app/`) идёт без обновления: менять каталог
разработчика нельзя.

Команды: `--install-release <файл.ndsupd> [--allow-downgrade]`, `--adopt`
(принять версию, привезённую установщиком), `--verify`, `--status`, `--stop`.

## Как версия проходит по сети: от первого узла до всех

Центрального сервера обновлений нет. Версия появляется на **одном** узле (его
называют источником), а остальные получают её друг от друга, по очереди, и каждый
следующий проверяет надёжность предыдущего. Ниже — путь версии целиком; детали
каждого шага — в разделах дальше.

### Шаги

1. **Появление.** Версию ставят на одном узле вручную: установщиком, файлом
   `.ndsupd` (`supervisor.mjs --install-release`) или готовым комплектом. Лаунчер
   запускает её пробным запуском (раздел «Лаунчер») и через 45 секунд без сбоев
   подтверждает. С этого момента узел — **источник**: он работает на новой версии и
   хранит её подписанный архив в `releases/<версия>/`.
2. **Замечание.** Версия (`version`) и так передаётся в анонсах и каталоге узлов.
   Остальные узлы раз в 30 секунд сравнивают её со своей. Увидев более новую,
   спрашивают у источника подписанный манифест и проверяют его **до скачивания**:
   подпись, канал, совместимость с этим узлом, «версия строго новее установленной»,
   «не помечена плохой на этом узле». Не прошло — версия отвергается на час.
3. **Слот.** Узел просит у источника слот на скачивание. Слотов мало (`updateSlots`,
   по умолчанию 2, и не больше одного на адрес). Нет свободных — ответ «занято,
   повторите через 5–15 секунд» (случайная пауза, чтобы очередь не пришла за
   слотом одновременно). Узел при этом пробует других источников: любого,
   кто уже работает на этой версии, и любого соседа в своей подсети — вдруг тот уже
   скачал её, но ещё не перезапустился.
4. **Скачивание и проверка.** Архив качается в пределах размера из подписанного
   манифеста, затем проверяются его сумма, состав и суммы каждого файла.
   Любое расхождение — отказ, а источник, отдавший мусор, не используется час.
   Проверенное раскладывается рядом с текущей версией (`app/<версия>/`,
   `releases/<версия>/`), но **не запускается**.
5. **Скачавший сам становится источником.** Как только архив проверен и лежит в
   `releases/`, узел может отдавать его другим — хотя ещё работает на старой
   версии. Поэтому нагрузка расходится цепочкой «А → Б → В», а не «все с А».
6. **Ожидание.** Узел ждёт два условия сразу:
   - **безопасность** — нет чужих аренд его устройств, нет его собственных
     подключений, не отдана сетевая карта, не идёт установка компонентов, никто не
     качает с него (раздел «Когда безопасно перезапускаться»);
   - **очередь** — сначала «канарейка»: источник должен проработать на новой
     версии `updateCanaryMinutes` (10 минут), потом узлы перезапускаются по одному с
     шагом `updateWaveStepSec` (30 секунд). Место в очереди у каждого узла своё
     (хеш от его идентификатора и версии), поэтому один и тот же узел не всегда
     последний. Договариваться между узлами не нужно: все считают одинаково.

   В режиме `ask` перед этим нужно ещё и ваше разрешение.
7. **Перезапуск и пробный запуск.** Узел записывает «пробная версия», выходит с кодом
   75, лаунчер запускает новую версию. Не подтвердила работоспособность (упала
   дважды или молчит 120 с) — **откат** на предыдущую, версия помечается плохой на
   этом узле, `config.json` возвращается. Подтвердила — старая остаётся как
   запасная.
8. **Дальше то же самое.** Узел, перезапустившийся в новую версию, теперь тоже
   источник «в работе»: следующие узлы считают очередь уже от него.

### Пример: три узла

Узел A получил версию 2.2.0 установщиком в 12:00. B и C на 2.1.0, настройки по
умолчанию.

| Время | Что происходит |
|---|---|
| 12:00 | A запустил 2.2.0, через 45 с лаунчер подтвердил. A — источник. |
| ≈12:00:30 | B и C заметили 2.2.0, проверили подпись манифеста у A. |
| ≈12:00:40 | B получил слот у A (слотов 2, оба узла сразу): скачал, проверил, подготовил. C — аналогично. Если бы слот был один, C получил бы «занято», подождал 5–15 с и скачал уже у B. |
| 12:00–12:10 | Оба в состоянии «Обновление готово к установке»: *«очередь: 1-й, перезапуск примерно через 570 с»* (и «2-й… через 600 с»). Они ждут, пока A отработает «канарейку» (10 минут). |
| 12:10:00 | Если B свободен — перезапуск, пробный запуск 2.2.0, подтверждение. |
| 12:10:30 | Если C свободен — то же. Если занят (чужая аренда) — ждёт и пишет, чего именно. |

Если 2.2.0 **плохая**: она откатится у A в первые минуты, а B и C уже скачали её, но
не перезапустились. Раз теперь ни один узел не работает на 2.2.0, они *не
перезапускаются* и пишут «ни один узел сейчас не работает на этой версии — ждём,
пока хотя бы один проверит её в работе». Плохая версия не доходит до рабочих
машин. (Кнопка «Перезапустить сейчас» обходит это — это ваше решение.)

### Что написано в интерфейсе

Над вкладками появляется полоса обновления:

| Заголовок | Что это значит |
|---|---|
| Проверка обновления | Узел проверяет манифест у соседа. |
| Скачивание обновления | Идёт загрузка архива. |
| Обновление в очереди | Все источники заняты (слоты кончились), повтор через указанное время. |
| Обновление готово к установке | Версия скачана и проверена, узел ждёт. Под заголовком — что именно: *«наши устройства заняты другими (N): они потеряют соединение»*, *«вы занимаете чужие устройства»*, *«очередь: N-й, перезапуск примерно через N с»* (это и есть оставшееся до своей очереди время), *«ждём, пока соседи проверят версию в работе»*. |
| Доступно обновление | Режим `ask`: версия готова, нужно ваше разрешение. |
| Перезапуск для обновления | Перезапуск уже идёт. |
| Проверка новой версии | Пробный запуск, около 45 секунд до подтверждения. |
| Нужен установщик | Версия не ставится по сети (нужен новый лаунчер или Node.js); есть ссылка на установщик у соседа. |
| Обновление не удалось | Причина показана; «Повторить» снимает отказы и пометки «плохая». |

Кнопки: **Разрешить установку** (режим `ask`), **Перезапустить сейчас** (обходит и
очередь, и проверку занятости — подключения к устройствам оборвутся; есть
подтверждение), **Повторить**.

### Настройки

| Параметр (`config.json`) | По умолчанию | Смысл |
|---|---|---|
| `updateMode` | `auto` у установленного, `ask` у переносимого комплекта | `auto` — ставить, когда безопасно; `ask` — скачивать, ставить после разрешения; `off` — выключено. Меняется и в настройках интерфейса. |
| `updateSlots` | 2 | Сколько соседей одновременно качают с этого узла. |
| `updateCanaryMinutes` | 10 | Сколько первый обновившийся узел работает до остальных. `0` — без выдержки (для проверок). |
| `updateWaveStepSec` | 30 | Пауза между перезапусками узлов в очереди. |

Для двух-трёх машин в тестовой сети выдержку разумно сократить
(`updateCanaryMinutes: 1`), для большой сети лучше оставить как есть: именно она
не даёт плохой версии пройти по всем узлам.

### Если что-то пошло не так

| Ситуация | Что делает узел |
|---|---|
| Подпись не сходится, неизвестный ключ, версия не новее | Версию отвергает, источник не использует; об этом в журнале и в полосе. |
| Все источники заняты | Ждёт и повторяет через 5–15 секунд. |
| Источник пропал во время скачивания | Берёт другой источник; недокачанное не используется. |
| Узел занят устройствами | Ждёт; кнопка «Перезапустить сейчас» — на ваше усмотрение. |
| Новая версия упала или молчит | Откат на предыдущую, версия помечена плохой на этом узле. |
| Версия отвергнута «плохой» зря | «Повторить» снимает пометку. |
| Нужен новый лаунчер/Node.js | «Нужен установщик» и ссылка на него. |
| Канарейка откатилась, а узел уже скачал версию | Не перезапускается, пока кто-то не проработает на ней нужное время. |

## Запуск ярлыком и второй экземпляр

Ярлыки (Пуск, рабочий стол) и последняя страница установщика запускают не
`start.bat`, а `launcher/open.vbs` через `wscript.exe`: окна консоли нет, значок —
`launcher/nds.ico` (тот же 🔌, что у вкладки интерфейса). Логика такая:

- приложение уже отвечает на порту интерфейса — просто открыть адрес в браузере;
- порт занят чужой программой — сказать об этом;
- не запущено — запустить лаунчер без окна, с запросом прав администратора, дождаться
  ответа (до 60 с) и открыть адрес. Отказ от запроса прав — сообщение об ошибке.

То же правило в самом лаунчере: если на порту интерфейса уже работает наше
приложение, второй экземпляр не стартует, лаунчер открывает адрес и выходит с
кодом 77 (раньше второй запуск падал на занятом порту, и лаунчер перезапускал
его каждые 5 с). Для отладки в меню «Пуск» есть ярлык «… (с окном консоли)» —
это `start.bat`.

## Раздача по сети

Протокол — в [PROTOCOL.md](PROTOCOL.md). Кратко: узел видит у соседа версию
новее (`version` уже есть в анонсе и каталоге), берёт у него подписанный
манифест, занимает слот на скачивание, качает архив, проверяет и раскладывает
рядом с текущей версией. Источник держит 2 слота (настройка `updateSlots`),
один слот на адрес; лишним отвечает `503 busy` со случайным `Retry-After`.
Скачавший узел сразу становится источником, хотя ещё не перезапущен: поэтому
спрашиваются и узлы, у которых версия выглядит старой. Порядок источников для
каждого узла свой (хеш от пары узлов и версии), своя подсеть раньше узлов из
других сетей (те — только если в подсети источника нет 10 минут).

Узел, отдавший мусор или оборвавший передачу, не используется час.

## Когда безопасно перезапускаться

Перезапуск сбрасывает чужие аренды наших устройств (занятость живёт в памяти),
обрывает наши подключения, возвращает отданную сетевую карту. Узел ждёт, пока:
нет чужих аренд, нет своих подключений, не отдана карта, не идёт установка
компонентов, никто не качает с него обновление. Причины ожидания показаны в
интерфейсе.

**Очередь.** Без координатора: узел, получивший версию раньше всех (источник),
перезапускается первым и работает `updateCanaryMinutes` (10) как «канарейка» —
если версия плохая, откат случится у одного узла. Затем остальные по очереди с
шагом `updateWaveStepSec` (30 с); место определяет хеш от идентификатора узла и
версии, у каждой версии порядок свой.

Если узел скачал версию, а потом ни один узел не работает на ней (канарейка
откатилась или недоступна), он **не перезапускается**: версию никто не проверил в
работе. Ждёт, пока она не проработает где-то нужное время, либо вашего «Перезапустить
сейчас».

Режимы (`updateMode`): `auto`, `ask` (качает, но ставит после разрешения в
интерфейсе), `off`. По умолчанию: у установленного приложения `auto`
(есть `installed.json`), у переносимого комплекта `ask`.

## Ключи

Ed25519, два с первого дня: `k1` — рабочий, `k2` — запасной (закрытую часть
унести с компьютера сборки на отдельный носитель). Открытые ключи вшиты в
`launcher/lib/keys.js`; закрытые лежат вне репозитория
(`~/.net-device-share-signing/`, путь — `NDS_SIGNING_KEY`, пароль —
`NDS_SIGNING_PASS`). Создание: `node scripts/release-keygen.mjs --id k1`.

Список ключей — часть лаунчера, и сетевое обновление его заменить не может
(иначе компрометация одного обновления отдала бы корень доверия). Ротация:
выпуск, подписанный `k1`, затем установщик с `{k2, k3}`. Потерян `k1` — выпуск,
подписанный `k2`, и установщик без `k1`.

Тестовый ключ (`NDS_UPDATE_TEST_KEY=<путь к открытому ключу>`) вправе
подписывать только канал `test`; включение пишется в журнал. Он нужен для
проверок на одной машине и в рабочей сборке не используется.

## Как выпустить версию

1. Поднять `version` в `package.json`.
2. `npm test` — проверки лаунчера, раздачи и сквозная (три узла на одной
   машине).
3. `node scripts/build-update.mjs` — подписанный релиз в `dist/release/<версия>/`
   (`.ndsupd`).
4. `npm run build` — переносимый комплект (если ключ есть, в раскладке с
   лаунчером; `--legacy-layout` — старая раскладка без обновления).
5. `npm run build:installer` — установщик (нужен Inno Setup 6).
6. Первый узел получает версию из `.ndsupd`:
   `node.exe launcher\supervisor.mjs --install-release файл.ndsupd` — и перезапускается.
   Остальные подтянут её сами.

Узлы версий до 2.1.0 не умеют обновляться: первую версию с механизмом
придётся поставить на каждый узел руками (установщиком или комплектом).

## Проверка на одной машине

`node --test test/update/*.test.mjs`. Сквозной тест поднимает три настоящих
узла (код из репозитория под лаунчером, тестовый ключ, порт обнаружения 47911,
`--backend mock`), проверяет раздачу, пробный запуск и подтверждение.

## Чего здесь нет и что сделано осознанно

- **Нет принудительного перезапуска по таймеру** и окна обслуживания: занятый
  узел ждёт сколько нужно. Есть кнопка «Перезапустить сейчас».
- **Обновление Node.js и драйверов** по сети не делается — только установщиком.
- **Подпись самого установщика** (Authenticode) не настроена: без сертификата
  SmartScreen предупредит. Страница `/download` показывает SHA-256 файла.
- **Правка подписи RPC** (метод, путь, время и nonce в подпись) и запрет
  `usbipdPath` из удалённых настроек (запуск файла с правами администратора по
  паролю интерфейса) — отдельными задачами и выпусками, с учётом
  совместимости в смешанной сети.
- Установщик Windows (`installer/nds.iss.tpl`, собирается `npm run build:installer`,
  нужен Inno Setup 6). **Проверено 17 октября на Windows 10** (не на чистой
  виртуальной машине): тихая установка с автозапуском и брандмауэром, каталог
  данных закрыт для обычного пользователя, установленное приложение запускается
  из Program Files с данными в ProgramData (обновление включено, режим `auto`),
  `/download` отдаёт установщик, остановка через `--stop`, тихое удаление
  убирает программу, задание и правила. **Не проверено:** установка поверх
  работающей старой версии, интерактивный мастер, удаление с вопросом про данные,
  чистая система без Node и драйверов.
