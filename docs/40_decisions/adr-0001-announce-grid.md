# ADR-0001: Масштабирование сетки анонсов присутствия

Статус: **предложено** — решение за человеком.
Дата: 2026-11-23.
Контекст решения: [ARCHITECTURE-REVIEW](../ARCHITECTURE-REVIEW.md) находка 1, [LOADTEST](../LOADTEST.md) раздел 2026-11-13.

## Контекст

Присутствие узла объявляется UDP-анонсами в broadcast и multicast; анонс
доставляется **каждому** из N сокетов подсети — deliveries = N²/интервал.
Замер на одной машине (2026-11-13): на 400 узлах 21 600 UDP-доставок/с,
показатель роста по ступеням ≈ 1,95 (квадратично), kernel CPU 85–89% — это
следующий слой после снятой лавины state-запросов; 400 узлов не сходятся.
На реальной сети узлы разнесены по машинам, но суммарный пакетный фон и
приём на каждом хосте те же N²/интервал.

Текущие параметры ([PROTOCOL](../PROTOCOL.md) «Тайминги»): интервал 3 с
(изменение) / 30 с (покой, удвоение), `next` в анонсе, таймаут соседа
`next × 3 + 2 с`, минимум 12 с.

Цель: снять потолок числа узлов на подсеть (ближняя — 250–500, дальняя —
тысячи, решается фиксацией НФТ в [REQUIREMENTS](../REQUIREMENTS.md)).

## Вариант A — темп анонсов растёт с размером сети

Узел знает число слышимых соседей N (реестр `PeerRegistry`); эффективный
интервал = базовый × max(1, N/K) в покое, активный темп — с потолком окна
(например, не быстрее 3 с × max(1, N/K/10)). Поле `next` уже произвольное —
формат пакета и старые узлы не затрагиваются.

* **Плюсы**: правка локальна (расчёт темпа в `discovery.js`), days-not-weeks,
  обратная совместимость полная — старые соседи верят `next`.
* **Минусы**: квадратичность остаётся структурно — активная фаза (массовое
  изменение состояния, холодный старт стойки) всё равно даёт N² всплеск;
  обнаружение падения деградирует: таймаут растёт вместе с `next`
  (N=400, K=10 → покой 30×40=1200 с — неприемлемо; нужен отдельный механизм
  быстрой пометки, напр. выборочный ping, уже есть `_checkSilent`).
* **Оценка эффекта**: потолок ~200–400 → ~1000–2000 узлов на подсеть
  (в покое; активная фаза требует гашения).

## Вариант B — одноадресная сетка присутствия

Broadcast остаётся только для обнаружения: редкий «я новенький» (раз в ~60 с
и на старте) и ответ на QUERY. Периодическое присутствие — unicast каждому
известному соседу по расписанию с джиттером; хеш состояния и `next` едут в
тех же пакетах.

* **Плюсы**: нагрузка строго линейна по N на хост; потолок по присутствию
  исчезает как класс; шум broadcast не тревожит сеть и sniffers.
* **Минусы**: смена семантики протокола присутствия (NDS/1 → версия сета),
  переходный период смешанной сети (новые узлы обязаны слать и редкий
  broadcast для старых — двойная работа), холодный старт стойки медленнее
  (обнаружение не пассивное), больше состояний для тестирования.
* **Оценка эффекта**: лимит перемещается в прикладную работу (state-канал),
  присутствие перестаёт быть узким местом на любом мыслимом N.

## Вариант C — A сейчас, B при подтверждённой потребности

Поэтапно: A как быстрый шаг снимает ближайший потолок без протокольных
последствий; B выполняется, когда НФТ зафиксирует потребность >1000 узлов
или замеры покажат, что активная фаза A бьёт по сходимости стойки.

## Рекомендация

**C**. A — малой кровью и без версии протокола; обязательное сопровождение —
гашение активной фазы (потолок burst-темпа) и удержание таймаута обнаружения
через ping молчунов (механизм уже есть). B — отдельным ADR-0002, когда
потребность подтверждена числом НФТ.

## Последствия

- При выборе A: правка `src/net/discovery.js` (расчёт темпа) + тесты темпа
  от N; LOADTEST-стенд повторить на 400/800.
- При выборе B: версия протокола, PROTOCOL.md переписывается, план
  перехода смешанной сети, e2e на обеих версиях.
- Без решения: потолок остаётся ~200–400 узлов на подсеть.
